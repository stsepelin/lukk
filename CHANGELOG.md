# Changelog

All notable changes to `lukk` will be documented in this file.

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`Events\RecoveryCodeUsed`**, dispatched once a recovery code is spent (`$user`, `$remaining`). NIST SP 800-63B-4 §4.2 asks that the subscriber be notified of an account recovery, and a recovery code is that — for the owner who lost their authenticator, or for whoever found the printed list. lukk sends no mail: listen for it, tell the user through another channel, and prompt a new set (at `$remaining === 0` the next lost authenticator has no way back). It carries the user as an identifier when queued, like the other user events, and fires whether or not the sign-in then completes, since the code is gone either way.

- **The account export discloses everything erasure deletes.** It gains `password_reset` (`requested_at` of a pending reset row on the configured broker's table and connection, or null — never the token), `two_factor.pending` (a secret enrolled and never confirmed) and `two_factor.recovery_codes_remaining` (never a code or its hash), and per session `amr` and `authenticated_at`. GDPR Art. 15 must disclose what Art. 17 destroys; these were deleted and not shown. `ExportAccount` takes the broker name as a new trailing optional argument.

- **Events for every authenticator bound or removed**, so an application can tell the user through another channel, as NIST SP 800-63B-4 §4.1.2.1 requires on binding. `TwoFactorAuthenticationConfirmed` fires when a TOTP is confirmed (enrolment alone binds nothing); `TwoFactorAuthenticationDisabled` when a secret, confirmed or pending, is removed, and not for an account that had none; `RecoveryCodesGenerated` when a new set replaces the old; `PasskeyRegistered` (with credential id and name) after a passkey is stored; `PasskeyDeleted` only when a credential was actually removed. Without them, a stolen session plus step-up could bind the attacker's key or remove the victim's second factor with nothing for the application to hang a notice on. Names follow Fortify's where one exists.

- **A `lukk.username` naming a column that does not exist is refused while `app.debug` is on.** A typo is not loud on its own: SQLite reads a double-quoted identifier matching no column as a string LITERAL, so `'mial'` turns the sign-in lookup into `"mial" = ?` — submitting `mial` as the identifier then matches every row, and the first account's password signs that account in. PostgreSQL and MySQL raise "column does not exist", which is loud but arrives as a 500 on the login route with no explanation. Sign-in now checks the column before it derives anything from the identifier, behind `app.debug` and only for the stock `EloquentUserProvider`, and names what to fix. Production pays one class comparison and a config read; debug pays one schema read per sign-in. A subclass that resolves a virtual identifier its own way is left alone, as is an application that has not migrated yet.

- **Unclaimed sessions (opt-in, `claim_seconds`).** A session whose sign-in response never reached its client — a dropped connection, an aborted request — is never used by that client, yet stayed alive until its refresh token expired. With `claim_seconds` set (e.g. 600), every session a sign-in starts is marked unclaimed in the revocation cache, and its first use claims it. Marked in `StartSession`, the one place families are born — except sessions with a pinned grant (personal access tokens, impersonation), which the application delivers and which may legitimately be first used days later. Claimed where a session is used: the guard, as it authenticates a request (one cache read per request while on; an integer compare and nothing else while off), and `RotateRefreshToken`, before its transaction and before any application callback.

  **Only the sign-in's original credential is ever revoked.** For a refresh token that is exact: the family's original row is the one with no predecessor, which `RefreshTokenRecord::$original` reports, and it must still be unrotated. An access token carries no lineage, so that half compares its `iat` with the marker and accepts a couple of seconds' tolerance — a fixed constant, deliberately not `leeway`: both timestamps are stamped by this server in one sign-in, while `leeway` measures signer-to-verifier clock drift and is meant to be tunable. It is bounded by the window's own `access_ttl + leeway` clamp below, past which the original access token has expired anyway. A credential minted later exists only because the session was refreshed, which is a use, so it claims whatever the marker says — a lost marker delete (a cache restored from a snapshot, a failover) therefore cannot log out a session in active use. The **effective window is at least `access_ttl + leeway` and at least 60 s**, which guarantees only that the original *access* token has expired before it could be used late. It does not protect a client that never touches this app within the window: one using the token only on another service and refreshing after that service's 401 arrives just past `access_ttl + leeway` and is revoked — it must call `POST {path}/session/claim`. A late original is revoked through `RevokeSession` (denylist first); on a verify-only service with no `refresh_tokens` table the storage failure is reported and the request still gets 401, since the denylist entry is what stops the family there.

  **Contract when on:** within the window every client must call `POST {path}/session/claim` (204, per guard, behind `auth:{guard}`, not pin-gated, throttled per user, mounted even with the feature off), or make an authenticated request to this app, or refresh; a client using the token only on another service must call the claim route. Revoking fires the new `Events\SessionUnclaimed`, not `RefreshTokenReused`: nothing was replayed, and that event is the theft alarm. A replacement `RefreshTokenRepository` must populate `RefreshTokenRecord::$original` — true only for the row it persisted with a null `$previousId`. One that leaves it unknown falls back to comparing `$createdAt` with the marker, which is a proximity test and therefore reads a successor minted moments after sign-in as the original; with neither field no original refresh row is recognised at all, nothing is ever revoked, and lukk logs a warning naming the guard once per worker process. Markers live in the denylist cache: losing them fails open (treated as claimed), and restoring an old snapshot can at most revoke a session still presenting its original sign-in refresh token after the window. Read per guard.

### Changed

- **BREAKING: the default guard must resolve its users from the provider it signs them in against.** Sign-in checks the password through `lukk.user_provider`; the `lukk-jwt` guard resolved the token's `sub` through `auth.guards.<default>.provider` (or `auth.defaults.provider`). Pointed at different providers, a `users` password minted a token for the `admins` row with the same id — an account takeover by configuration, with no error anywhere. Boot now refuses that configuration and names both settings. See UPGRADE.md.

- **BREAKING: an identifier carrying an invisible character is refused** on sign-in, registration, forgot- and reset-password: control characters (C0 and C1, NUL included), format characters (`\p{Cf}`: zero-width space and joiners, soft hyphen, bidi controls), enclosing marks, U+034F, and any whitespace other than the ASCII space. Combining marks in general are not refused (Devanagari, Thai, Arabic and Hebrew need them), nor are precomposed accented letters. Registration's `name` refuses NUL. See Fixed for why, and UPGRADE.md.

- **Recording a failure and locking are separate steps** (`Contracts\ReservesLockoutAttempts`, implemented by `DatabaseLockoutRepository`). Login, step-up confirmation, password change and the two-factor challenge still count an attempt BEFORE checking it, and refuse on the post-increment count, so concurrent requests cannot overrun the cap — but the lock, and `AccountLocked`, now land only once the check FAILED. The attempt that reached the cap with the right credential used to lock the account, fire `AccountLocked`, then release it and fire `AccountReleased`: an app notifying on those told the owner someone was breaking in, about their own sign-in. A count past the cap on a row that is not locked (a crash between the reservation and the verdict) is locked by the next attempt, so `release_after` can still time it. A repository implementing only `LockoutRepository` keeps the old behaviour through `recordFailure()`.

- **`DatabaseRefreshTokenRepository::persist()` writes with `saveQuietly()`, and throws when nothing was written.** It runs inside the rotate transaction, under the row lock, where no application code may run; `save()` fired the model's events, so an observer on a `useRefreshTokenModel` subclass ran there — and on PostgreSQL a swallowed failing query in it turned COMMIT into a silent ROLLBACK, while a `creating` listener returning false cancelled the write: both handed back a refresh token that was never stored. See UPGRADE.md.

- **BREAKING: `Lukk\Contracts\WebAuthnCeremony` reports what an assertion PROVED.** `verifyAssertion()` returns a `Lukk\Support\PasskeyAssertion` (`signCount`, `userVerified`, `multiFactor`) instead of an `int`, and takes an optional `?string $userVerification` to enforce for that one ceremony; `authenticationOptions()` takes the same optional argument; and there is a new `isMultiFactor(PasskeyRecord): bool`. A custom implementation must adopt all three — PHP raises a fatal on the mismatch at class-load time, an `E_ERROR` the framework's handler never renders, so it surfaces on the first passkey request rather than at boot. **Report `multiFactor` true only for a credential that was already `uvInitialized` before this ceremony**: lukk skips a user's enrolled second factor on the strength of it. See UPGRADE.md.

- **BREAKING: `amr` uses only values registered under RFC 8176.** `webauthn` was never in the IANA registry, so no standard consumer could interpret it. A passkey is now `["pop","user"]` — proof of possession of a key plus the user-presence test — with `"mfa"` added when the assertion was multi-factor; a password with a one-time code is `["pwd","otp","mfa"]`. A single-factor passkey followed by a TOTP is `["pop","user","otp"]` and deliberately NOT `mfa`: both are possession (NIST SP 800-63B-4 §3.1.4, §3.1.6), and §2.2.1 requires a password or biometric comparison for two single-factor authenticators to reach AAL2. Anything gating on `"webauthn"` must move to `"pop"`, and on "was this multi-factor" to `"mfa"`.

- **BREAKING: `amr` is stored with the session, adding a `refresh_tokens.amr` column and a trailing argument to `RefreshTokenRepository::persist()`.** `amr` (RFC 8176 — how the session was authenticated: `["pwd"]`, `["pwd","otp","mfa"]`, `["pop","user"]`) was stamped only by `StartSession`, so it disappeared from the FIRST refreshed access token. A route gated on it therefore stopped working roughly one `access_ttl` into every session — fail-closed if the gate was written tightly, **fail-open** if written as `!isset($amr) || in_array(...)` — while the docs presented it as durable. It is now persisted with the family and carried forward by every rotation, and is **reserved** like `scope` and `pin`: applied after the `tokenClaimsUsing` merge, so a claims hook can neither forge an authentication method the session never used nor erase the real one.

  **What you must do.** Add a nullable `text` `amr` column to `refresh_tokens` with a migration of your own. The column went into the existing `create_refresh_tokens_table`, as `guard` and `scope` did, so a fresh install gets it from that file, but republishing it does not help an existing one: the copy gets a new timestamp and fails with "table already exists". Until you do, nothing breaks: `persist()` writes `amr` only when it has one and reads a missing attribute as null, which is the pre-upgrade behaviour. If you implement `RefreshTokenRepository` or override `persist()`, add the trailing `?string $amr = null` and round-trip it onto `RefreshTokenRecord::$amr` as you do `scope`; PHP fatals on a mismatched signature, so this surfaces at once rather than silently. A repository that ignores it keeps the old behaviour. See UPGRADE.md.

- **`POST /auth/logout` ends a session with an expired access token.** It sat behind `auth:{guard}`, so the most ordinary client state — an idle tab whose access token had lapsed — got a 401, nothing was revoked, and in cookie mode the `__Host-refresh` cookie stayed valid for its whole TTL (RFC 7009 §2.1–2.2, ASVS 5.0 V7.4.1). Logout now accepts **either** credential: a valid access token revokes its family exactly as before (and still authenticates the request as its user), and the refresh token the client holds revokes the family it belongs to on that guard. An expired access token is **not** honoured on its own, even with a good signature: that would make every access token that ever reached a log a 30-day capability to end its session, and needs a second verification path that skips `exp`. The answer is always `204` — nothing reveals whether a token existed. A consumed token presented past grace dispatches `RefreshTokenReused` exactly as `/refresh` would; a token rotated inside grace ends the session, sibling included, without the event. A valid bearer with no `fid` (a co-issuer's token) now has its `jti` denylisted for the rest of its life, where before logout did nothing for it.

  **CSRF.** `SameSite=Strict` does not stop a same-*site* sibling page (evil.example.com → api.example.com) from form-POSTing with the cookie, and even cross-site the clearing `Set-Cookie` is stored after a top-level navigation. The refresh cookie is therefore used — and cleared — only on a request a form cannot produce: `Content-Type: application/json` (matched on the MIME essence, since `text/plain; x=/json` is CORS-safelisted) or `Sec-Fetch-Site: same-origin`/`none`. A direct-mode SPA on a sibling subdomain sends `{}` as JSON. The body `refresh_token` is read from a JSON body only. `/refresh` is unchanged: a forged refresh only rotates the cookie into a response the attacker cannot read.

  **Throttling.** No route throttle: a per-IP limit shared with `/refresh` let junk refresh traffic from one address (a NAT, a BFF not forwarding the client) turn a valid-bearer logout into a 429. Only the refresh-token lookup is metered, on its own per-guard, per-caller bucket with the `rate_limits.refresh` limits, and only unproductive lookups count — probing always misses, while a token that resolves to a live family (valid, rotated or expired) costs nothing, so a BFF pays nothing for the logouts that actually end a session, however many users it ends them for from one address. A token whose family is **already revoked** counts like a miss and does no work: re-revoking wrote the denylist and ran UPDATEs on every request, so one known dead token was an unmetered write amplifier — which also means a logout retried or replayed after the session ended does spend the budget. An exhausted bucket is refused before the lookup, even for a real token, since existence is only knowable by looking; a miss is counted atomically after it, and the counting request's own response never depends on that count. The budget itself remains a side channel — max−1 misses, a candidate, then a miss answers 204 or 429 — accepted because it costs a whole budget per bit of a 256-bit token. A request carrying a valid bearer is not metered — the bearer is revoked by the call, so it cannot be replayed for more lookups — so ordinary BFF logouts no longer exhaust the bucket. When the lookup *is* throttled the answer is **429 with `Retry-After`** and the cookie is left in place: a 204 there would tell the client it had logged out while its refresh token stayed valid (ASVS 5.0 V7.4.1), and a 429 reveals nothing about the token.

- **`features.logout_all` is honoured.** It was documented as a switch and read by nothing. `false` now leaves `DELETE /auth/sessions` unmounted, read per guard like the other route gates. Default stays `true`.

- **Changing the password needs the account's strongest session, like a password step-up.** `POST /auth/password` now runs the same check as `POST /auth/confirm-password` (NIST SP 800-63B-4 §4.1.2.1): on an account with an enforced TOTP or a user-verifying passkey, a session that is not a recent multi-factor one — `amr` without `mfa`, no `amr` at all, or an `mfa` sign-in older than `confirm.mfa_max_age` — is refused with `422` on `current_password`, before the current password is checked, so a refusal spends no lockout attempt. The new password replaces an authenticator, so knowing the current one is not enough in a password-only session. `EnsurePasswordStepUpMeetsAccountLevel::__invoke()` takes two optional arguments: the input the refusal is reported on, and its message — change-password's says to sign in again with the second factor or a user-verifying passkey, since that route takes no step-up confirmation.

- **Re-confirming two-factor that is already on answers `409`.** It answered `204`, overwrote `two_factor_confirmed_at` and fired `TwoFactorAuthenticationConfirmed` again — a "new authenticator" notice for no change. Mirrors enrolment, which already refuses an account that has two-factor.

- **Regenerating recovery codes on an account without two-factor answers `409`.** Eight codes nothing ever asks for, and a `RecoveryCodesGenerated` notice about an authenticator the account does not have. Allowed while two-factor is on or being enrolled (a secret stored, not yet confirmed).

- **`AccountReleased` fires only when a HELD lock is cleared.** It fired whenever a counter row was deleted, so every successful sign-in after a single typo told an audit log that a locked account had been unlocked. Clearing a counter that never reached the cap, or a lock already past `release_after` (whose expiry announces nothing), no longer fires it. `LockoutRepository::release()` still returns the rows it cleared; the contract's docblock now says to fire the event for a held lock only. Whether a lock is held is decided by the deleting statements themselves — the held lock is deleted (and announced) first, then only rows that hold no lock — so a lock taken by a concurrent failure mid-release is either announced or left standing, never lifted silently. The `release_after` bound in those statements is rounded up to the whole second, since `locked_at` is stored to the second and a bound with its fraction dropped took a lock `locked()` already called lifted for held — announcing it for up to a second after it had expired. `lukk:release` says which happened: "Released the login lock…" for a held lock, "No login lock was held…; cleared its failure count." otherwise.

- **The account export discloses every passkey field erasure destroys, and its timestamps are all ISO-8601.** `passkeys[]` gains `created_at`, `aaguid` and `transports` (GDPR Art. 15 should disclose what Art. 17 deletes), and `last_used_at` is an ISO-8601 string like every other time in the export rather than a unix integer. The COSE public key and the sign counter stay out. Each entry is mapped through an allowlist and typed, so a rebound `PasskeyRepository` returning more than it should cannot publish it. `PasskeyRepository::summariesForUser()` may return the three new keys (optional, so a 0.6 store still conforms).

- **Per-guard `two_factor.challenge_ttl`, `confirm.ttl` and `confirm.header`.** All three were read from the global block, while the routes they serve mount on every guard and the tokens they shape are signed with that guard's key. They are now read through the guard's resolved config, like `features.two_factor` and `confirm.mfa_max_age` already were; `confirm.header` is the setting of the guard that authenticated the request, the same guard whose key verifies the confirmation.

- **The refresh cookie lives only as long as its session.** A family's expiry is absolute — fixed at sign-in and inherited by every successor — but each rotation re-set the cookie for the full `refresh_ttl`, so late in a session's life the browser held it for weeks past the point the server would accept it. The cookie's lifetime is now what is left of the family's (never less than a second: zero would make it a session cookie). `TokenPair` carries the expiry in a new optional `refreshExpiresAt`, which is not serialised; the response stays `no-store`.

### Removed

- **`features.rotation`, `features.reuse_detection`, `features.denylist`.** Never read: rotation, reuse detection and the denylist are the security model and cannot be switched off. A published config still carrying them keeps working; the keys are inert.

### Fixed

- **Respelling the identifier no longer buys fresh login-throttle buckets.** The throttle keys on the identifier's fold, and with the lockout off (the default) its IP-independent account bucket is the only cap on a distributed guesser (NIST SP 800-63B-4 §3.2.2). On PostgreSQL pdo_pgsql ends a bound string at NUL, so `victim@example.com\0<n>` looked up the victim while each `<n>` keyed a new bucket; on MySQL `utf8mb4_unicode_ci` ignores U+200B, U+034F and other zero-weight code points and pads trailing U+3000, which matched the victim while `Str::transliterate` kept them apart. Such identifiers are now refused (see Changed), and the fold strips control, format and combining characters and trims Unicode whitespace, so it is never finer than the database's equality. Pinned on both engines in `tests/Concurrency/IdentifierRespellingTest.php`. On PostgreSQL a registration carrying a NUL also stored a truncated value `unique` had never checked.

- **A blank identifier no longer puts every caller in one account bucket.** With `Lukk::authenticateUsing()` reading a field other than `lukk.username`, every attempt's identifier was empty, and the IP-independent bucket keyed on it was one for the whole application: `account_max_attempts` wrong guesses from anywhere answered every sign-in 429. With nothing to key an account on, that bucket is skipped and the per-IP ones apply.

- **Two-factor guesses are counted before they are checked.** The per-account limiter read `tooManyAttempts()` and hit only after a failure, so concurrent guesses all passed the read: a burst got as many guesses as it had requests (RFC 6238 §5.2, NIST SP 800-63B-4 §3.2.2). It now increments first and refuses on the post-increment count; a success clears it.

- **An unverified account's two-factor challenge is refused before the factor is spent.** Under `email_verification.block_unverified_login`, a challenge that outlived the account's verified state was refused only after `ChallengeTwoFactor` had verified the factor, so a single-use recovery code was burned on a sign-in that was always going to be refused. Checked first now, like a stale password; the check after verification still closes the race with an email change.

- **Concurrent first failures for one account no longer deadlock on MySQL.** The lockout counter was created inside its counting transaction after a `SELECT … FOR UPDATE` on the absent row, which under REPEATABLE READ takes a gap lock; simultaneous first failures each held it and InnoDB killed all but one with 1213 — a 500 on `/auth/login` and an uncounted guess, measured at seven of eight. The row is now created first, in autocommit, with `insertOrIgnore`.

- **A co-issuer's non-UUID `fid` is no longer a 500 on PostgreSQL.** `family_id` is a native `uuid` column there, and comparing `42` or `"sess_42"` with it raised 22P02 on change-password, logout (after its denylist write), `DELETE /auth/sessions(/others)` and the pinned-ability gate on step-up confirmation. Such an id names no family of lukk's: not pinned, nothing to revoke, and no exception from "others". Likewise a `sub` an integer key could never hold (`"admin"`, past bigint, `"1.5"`) is refused with 401 before the user lookup instead of 22P02/22003.

- **An empty `fid` names no session.** `DELETE /auth/sessions/others` read `"fid": ""` as a family, excepted none, and logged out every device; it now answers 409, as for a token with no `fid`.

- **`DELETE /auth/sessions` ends the token that asked.** A co-issuer's bearer names no family of lukk's, so "log out everywhere" left it live until it expired, while `POST /auth/logout` with the same token denylisted it (RFC 7009 §2.1). It is now ended the same way: its family on the denylist when it names one, otherwise its `jti` for the rest of its life.

- **Login was not constant-time, in two ways, both measured.** The unknown-identifier branch verified the submitted password against a dummy hash memoized in a function `static` — which PHP resets at request shutdown, so under PHP-FPM every such attempt paid `Hash::make` **plus** `Hash::check` while a real account paid a single `check`. At bcrypt cost 12 that is 472 ms against 236 ms: a 2x account-existence oracle, inverted from the one the equalizer exists to close but just as usable. Separately, an account whose `password` column is null or empty answered in ~0 ms, because `EloquentUserProvider::validateCredentials` and `AbstractHasher::check` both return before hashing — and that is the passkey-only, SSO and invited-not-yet-set shape, i.e. exactly the accounts worth pivoting to a passkey or reset phish, a shape this package creates itself. Every failing path now costs exactly one key derivation. Neither was visible to the suite: the memo hides the cost from the second request onward in a shared process, and both tests that claimed to cover it were written around the implementation rather than the property (one pinned `Hash::check` specifically; the other allowed `makes <= 1`, excusing the process-static memo in a comment). They are replaced by one that counts derivation WORK across all three account shapes.

- **Login is now equalized by wall clock, not only by work, and a legacy-cost hash no longer betrays its account.** Counting one derivation per path was not enough: `Hash::check` runs at the cost STORED in the hash, while the unknown-identifier branch derived at the configured cost, so an install that had raised `hashing.bcrypt.rounds` answered unknown identifiers measurably slower than its older accounts. A failing attempt against a weak stored hash now derives once more at the configured cost; a successful one rehashes it (honouring `hashing.rehash_on_login`, as the framework's own guard does), so the gap closes as users sign in. On top of that, the whole credential check runs inside `Illuminate\Support\Timebox`, padded to the new `login_timebox_micros` (default 500 ms, `LUKK_LOGIN_TIMEBOX_MICROS`) on every failure and returning early only on success — which is what an attacker already knows the answer to. The budget pads; it never shortens a slow hash, so set it above your worst-case derivation. Read per guard.

- **`POST /auth/forgot-password` was an account-existence oracle by response time.** The broker writes a token row and sends (or queues) a notification only for a real address, and the framework's own 200 ms `Timebox` inside `PasswordBroker` is shorter than a synchronous mail send. The whole call is now boxed to `password_reset.timebox_micros` (default one second, `LUKK_RESET_TIMEBOX_MICROS`). The earlier equalizer, a `Hash::make` after an unknown address, matched the broker's token hash but not the mail, so it is removed. Queue the notification (`ShouldQueue`) if one second is too long for your users; the budget only has to exceed the slowest real path.

- **Passkey login skipped a confirmed second factor unconditionally.** On an install whose `user_verification` is below `required`, `web-auth/webauthn-lib` never reads the UV flag, so whoever held the authenticator got a full session without the TOTP the user had enrolled. The decision is now made per ASSERTION, as WebAuthn L3 §4 describes: a passkey stands in for the second factor only when this assertion carries the UV flag AND the credential was already `uvInitialized` before the ceremony. The second condition is the spec's own — the UV flag "MUST NOT be relied upon" otherwise — and it closes the concrete case of a stolen key with no PIN, whose thief sets a PIN and from then on presents UV. Config no longer decides it: config describes what was asked for, the assertion is what happened, and the spec permits relying on it "even when user verification was not required". lukk never promotes `uvInitialized` itself, because the spec says that SHOULD take an additional factor equivalent to user verification, and a TOTP is possession, not equivalent.

  **Step-up follows the account's own level.** `POST /auth/confirm-passkey` mints the token that binds and removes authenticators, so it must authenticate at "the maximum AAL currently available in the subscriber account" (NIST SP 800-63B-4 §4.1.2.1). A multi-factor assertion always meets it. A single-factor one is refused when the account can reach AAL2 — it has a password, or any multi-factor passkey — and accepted only for a password-less account whose credentials are all single-factor, which has nothing stronger and would otherwise be stranded. The new authenticated `POST /auth/confirm-passkey/options` asks the authenticator for `userVerification: required` in exactly the first case (WebAuthn L3 §5.8.6), lists the user's own credentials so a non-discoverable key works, and the same requirement is ENFORCED on the assertion, not merely hinted. A refused step-up answers **422 on `credential`**, like a failed verification, never 403: on a step-up route 403 means the token itself may never confirm, and clients abandon the prompt on it.

- **A look-alike account could reset another account's login failure count.** The IP-independent `account_max_attempts` bucket — with the persistent lockout off, which is the default, the only cap on consecutive failures (NIST SP 800-63B-4 §3.2.2) — is keyed on the case- and script-folded identifier, so `аdmin@y.com` (Cyrillic а) and `admin@y.com` share it, and a success cleared it: the look-alike's owner could sign in between bursts to reset the victim's count. A success now clears only the caller's per-address bucket; the IP-independent one decays and nothing else, which costs a real user nothing short of `account_max_attempts` failures in one window. Both buckets stay keyed on the fold alone, deliberately: a bucket keyed on the resolved account exists only for real accounts, and a spelling the database does not resolve counts in the fold alone, so the two drift apart and the throttle's timing — `Retry-After`, and after one bucket expires the status itself — answers whether an account exists. The account the identifier names is still looked up once, before the throttle, and the password checked against that row, so sign-in makes one query fewer with the lockout on.

- **Passkey options carry a `timeout`, the prompt gets five minutes, and an answer given at the last moment is accepted.** Without a `timeout` the browser's own default — often five minutes — applied while lukk forgot the challenge after two, so a slow PIN or biometric entry ended in "could not be verified"; options now send `passkeys.challenge_ttl`. The server then forgot the challenge at the same instant the browser's `timeout` closed the prompt (WebAuthn L3 §5.4, §5.5), so an assertion completed near the end was refused while still in transit; the challenge now outlives the advertised timeout by 30 seconds. `passkeys.challenge_ttl` defaults to 300 (was 120), the WebAuthn L3 §15.1 recommendation for a ceremony that verifies the user — a PIN, a biometric, or a phone reached over hybrid transport, which two minutes routinely cut off. An explicit `LUKK_PASSKEY_CHALLENGE_TTL` is kept.

- **Account erasure and export reach a rebound `PasskeyRepository`.** Both checked for a table literally named `passkeys` before touching the repository, so a store that is not that table — Redis, another service, a renamed model — was skipped: erasure reported success while the passkeys survived, and the export omitted them. The database store now answers an unpublished table itself (on its model's own connection and table name), and the actions call whatever store is bound — as does the new `password_reset.revoke_passkeys`.

- **Body mode no longer reads a refresh cookie on `/refresh`.** Only cookie mode puts `RefuseForgeableCookieGrant` in front of the route, yet the cookie was read in both. A cookie left over from cookie mode, or planted by a sibling subdomain, could therefore be consumed by any cross-site form: the attacker never sees the new pair, but the victim's next refresh presents the rotated token, and past grace that revokes the family. Body mode never sets the cookie, so no working client is affected.

- **Transactions and schema checks run on the connection the model lives on.** Refresh-token rotation and bulk revocation opened `DB::transaction` on the default connection while querying a `useRefreshTokenModel` subclass's own, so the row lock was taken in autocommit and released at once — rotation and reuse detection were not atomic. Recovery-code redemption did the same with a user model on a directory connection, so two concurrent redemptions of one code could both succeed. And erasure checked the password broker's table on the default connection, so a broker with `auth.passwords.*.connection` kept the reset row, a plaintext email address, after the account was deleted.

- **The grace window works on PostgreSQL and MySQL.** Counting a family's live tokens — run on every re-consumption inside grace — compared the datetime `expires_at` with a Unix integer. PostgreSQL refused the query, so two tabs refreshing with one token got a 500 and the retry, past grace, revoked the whole family: a false logout under ordinary concurrency. MySQL counted nothing, so `RefreshFamilyForked` could never fire; sqlite, the test suite's engine, counted expired rows, which is why nothing noticed. The concurrency suite now runs an in-grace sibling rotation on both engines.

- **Account erasure stays atomic across every connection it writes to.** Opening the erasure transaction on the refresh-token store's connection left the passkey, lockout and reset-row deletes on the default connection in autocommit when `useRefreshTokenModel` lives elsewhere, so a disposal that then threw kept the user and lost their credentials. Erasure now opens a transaction on the default connection, the password broker's and the token store's, nested so a shared one is a savepoint. A broker connection may be named by an enum, backed or pure.

- **Access-token time claims must be timestamps.** `exp`, and `iat`/`nbf` when present, must be a number (or numeric string) between the epoch and the end of year 9999; a fraction stays valid (RFC 7519 §2). A co-issuer could otherwise stamp `exp: 1e30` and every later integer cast warned into a 500 — on logout, logout-all and, with `claim_seconds` on, every authenticated request. Two-factor and step-up challenges take the same upper bound on `exp`, whose remaining life `consume()` hands to the cache as a TTL that Redis refuses near `PHP_INT_MAX`.

- **A recovery code stored under a hasher the app has since left is no match, not a 500** — the one path left to a user who lost their authenticator died after a move to argon2id with `verify` on.

- **A future `auth_time` is not a recent one.** The password step-up's multi-factor allowance accepted any `auth_time` not older than `confirm.mfa_max_age`, including one ahead of the clock. A co-issuer's token can carry any `auth_time`. Anything more than `leeway` ahead is now refused, and one before the epoch is refused too (a co-issuer's out-of-range value made the integer cast warn into a 500; the comparison is now done in floats, so a far-future one is refused as future); a fractional `auth_time`, which OIDC Core §2 allows, counts as the second it falls in.

- **Registration, reset and change-password require the new password to be a string**, under every rule set, rather than relying on `Password::defaults()`: an app registering its own rule object there let a JSON number through to be cast and stored.

- **Confirm-password and change-password answer 422, not 500, on a stored hash the hasher refuses** (another algorithm, or a `$2b$` import with `hashing.bcrypt.verify` on). Sign-in already failed that closed.

- **Erasure and export reach a rebound `LockoutRepository`.** Like the passkey store, both checked for a `lukk_lockouts` table before calling the repository, so a store that is not that table kept a deleted account's counters and left them out of the export. The database stores now check their own tables, on their models' own connections.

- **A refresh token from an already-revoked session no longer re-runs the revocation.** `/refresh` re-revoked the family on every presentation — a denylist write and two UPDATEs — so one dead token replayed at an unauthenticated route was a write amplifier; logout already treated it as dead. A token whose own row is revoked is now refused with the same `revoked` reason and nothing written. A live row whose family's denylist entry is set (a revoke still in flight) is still revoked again after commit, so the successor it just inserted is caught.

- **A passkey sign count never moves backwards.** Two concurrent assertions each wrote `max(stored, theirs)` from the same stale read, so the lower could land last and roll the count back, after which a clone presenting the higher value passed (WebAuthn L3 §7.2). The count is written only while the stored one is lower.

- **`lukk:secret --guard` refuses a name that is not a valid environment variable.** The name went into a regex unescaped, so `--guard=a.b` overwrote another guard's `LUKK_AXB_SECRET` line.

- **Three passkey gaps, each a contract change.** A step-up now passes the account it expects to the ceremony as the expected user handle (WebAuthn L3 §7.2 step 6), so a returned `userHandle` naming another account is refused: `WebAuthnCeremony::verifyAssertion()` takes a trailing `int|string|null $owner`. Two concurrent assertions with the same signature counter both passed, because each read the stored counter before either wrote it; the forward-only update now reports whether it won (`PasskeyRepository::updateSignCount()` returns `bool`), and the loser is treated as a clone — refused, with `PasskeyCloneDetected` — as WebAuthn L3 §6.1.1 directs for a counter that did not advance. And a passkey clears the password-confirm lockout only once every check has passed — a step-up refused for the account's level used to clear it first — and a sign-in clears it only when it grants a session on a multi-factor assertion: a presence-only key proves possession alone, so with a stolen access token it wiped the count between password guesses, which made them unlimited (NIST SP 800-63B-4 §3.2.2). A credential deleted mid-ceremony is refused without a clone alarm — whatever its counter did: a synced passkey reports 0 forever, and gating the check on an advancing counter let a passkey just removed (a stolen one, say) still sign in. See UPGRADE.md.

- **Registration verifies the credential against the algorithms lukk advertised.** WebAuthn L3 §7.1 step 22 checks the key's `alg` against the creation options' `pubKeyCredParams`; the options rebuilt at verification listed none, so the library substituted its own default. It equals ES256 and RS256 today, so nothing changes now, but both sides now share one list and a library change cannot widen what registration accepts.

- **BREAKING: a `lukk.username` that cannot work as a column is refused by name.** `EloquentUserProvider::retrieveByCredentials()` drops every key containing "password", so such a column looked nothing up and every sign-in failed with an ordinary 422; a dot read nested request input and became a table-qualified column. Anything but a plain column name (letters, digits, underscores, not containing "password") now throws an `InvalidArgumentException` that names the setting.

- **A lock on an identifier that names no account no longer stores it in plain text.** The persistent lockout keyed such a lock by the normalized identifier — often a real person's address, a typo of it, or a stranger's — and a held lock is never pruned, while `release_after` defaults to 0, so the address could sit in the table indefinitely with no account through which its owner could have it erased (GDPR Art. 5(1)(c)). It is now `idn:sha256:<digest>`; the counter only compares for equality. Locks written before the upgrade keep their old key, and `lukk:release`, account erasure and the export all still find them.

- **A wrong recovery code no longer holds a lock on the user's row.** Every stored code was checked with a password hash inside `lockForUpdate()`, so one wrong guess held the row for as long as eight to a hundred derivations take, stalling every other write to the account. The match is now found first, without a lock, and only spending it locks: the row is re-read and the matched hash removed if it is still there, so concurrent redemptions still spend a code once.

- **`lukk.confirm` works whichever side of `auth:{guard}` a route lists it.** Middleware runs in declaration order unless it is in the kernel's priority list, and the step-up gate was not, so `['lukk.confirm', 'auth:api']` read no user and answered 423 to a valid confirmation. It is now sorted after authentication, like the ability gates.

- **BREAKING (cookie mode): login CSRF.** `SameSite=Strict` stops the refresh cookie being *sent* cross-site, not being *set*: RFC 6265bis §5.7 stores a SameSite cookie from the response to a cross-site top-level navigation. Any site could auto-submit a form to `/auth/login` with the attacker's credentials, or to `/auth/refresh` with the attacker's token, and plant the attacker's session in the victim's browser; the victim's app then refreshed into the attacker's account. In cookie mode, `login`, `register`, `refresh`, `two-factor-challenge` and `passkeys/login` now accept only a request a form cannot produce — a JSON body, or `Sec-Fetch-Site: same-origin`/`none` — and answer **415** otherwise, the rule `/logout` already applied. lukk-js already sends JSON. Body mode is unchanged.

- **A password step-up now meets the account's own level, as the passkey step-up already did.** The confirmation token binds and removes authenticators, which NIST SP 800-63B-4 §4.1.2.1 puts at "the maximum AAL currently available in the subscriber account". §2.2.3 lets an AAL2 session reauthenticate with one factor, so `POST /auth/confirm-password` still works inside a session whose `amr` carries `mfa`, and on any account with nothing stronger than the password. It is refused (422 on `password`) on an account with an enforced second factor or a user-verifying passkey when the session's token does not say it was multi-factor — including a token with no `amr` at all, since the claim goes missing in ordinary ways (a refresh on a schema without the `amr` column, `startSession()`, a co-issuer). Such a session confirms with a user-verifying passkey, or signs in again with its second factor. An enrolled TOTP counts only where the guard enforces two-factor, or a user whose guard has it switched off could never step up. The refusal comes before the password is checked, so it spends no lockout attempt. `Lukk::actingAs()`, which presents no token, keeps the old rule.

- **New `password_reset.revoke_passkeys` (default false).** A reset keeps the account's passkeys, as it keeps the second factor, so a passkey an attacker enrolled while holding the password, or on an account squatted before its owner verified it, outlives the recovery. With this on, a reset removes every passkey and dispatches `PasskeyDeleted` for each. It only means something with `revoke_sessions` on (the default): a session that survives the reset can step up and enroll a new passkey straight away.

- **Reset and change-password write the column the model names.** Both wrote a `password` attribute, while sign-in read `getAuthPasswordName()`, so a model with another password column got a 500 after the current password had been verified.

- **The opt-in lockout no longer answers whether an account exists.** Its login counter was the account for a spelling that resolves and the identifier's fold for any other, so failures on a spelling the database never resolves (a Cyrillic look-alike; another case on a binary collation) locked a non-account's canonical spelling and not a real account's: 423 versus 422. Every login failure now counts against the fold, and against the account too when one resolves; either locks. Only the account's own success, reset or password change releases its account counter, so a look-alike account still cannot release the victim; it can, as before 0.6, be locked by the victim's failures. When both lock, `AccountLocked` fires for each — the `idn:` one names no one. With `release_after` above zero the two counters can expire apart, which leaves a slow timing residue; the default (0) has none.

- **Per-guard lockout and login limits are honoured.** `features.lockout`, the `lockout` block, `rate_limits.login.*` and `rate_limits.two_factor.*` were read from the global block, so an extra guard that hardened itself — the lockout on, tighter caps, as the multiple-guards docs recommend for an admin guard — silently got neither. They are read per guard now, like `features.abilities`.

- **Under bcrypt, a new password over 72 bytes is refused.** bcrypt reads only the first 72 bytes, so a longer password was stored truncated and any string sharing that prefix signed in (NIST SP 800-63B-4 §3.1.1.2 requires verifying the whole password); with Laravel's `hashing.bcrypt.limit` on, it was a 500 instead. Register, reset and change-password now answer 422 — registration also when `Lukk::registerValidation()` replaces the rules, whose set naturally omitted it (an array password there 500'd in the default create, and is now a 422 too). Sign-in, password step-up and change-password's current password refuse one over 72 bytes against a bcrypt-stored hash (`$2a$`, `$2b$`, `$2x$` or `$2y$`), which they could only verify in part. Every earlier release stored such a password truncated, so its owner is typing the right one: they are told to reset it ("This password is longer than 72 bytes…") rather than that it is wrong — an answer only a caller whose first 72 bytes match can reach, and one the old code signed straight in. A NUL byte under a custom rule set is a 422 too. The same checks apply to a rebound `RegisterRequest` subclass that overrides `rules()`. With a custom rule set and a `registerUsing()` hook, the string and NUL checks still apply (any hook that hashes would 500 on either), but not the 72-byte rule, which is bcrypt's: the hook may hand the password to an IdP that takes longer ones. Other drivers are unaffected; argon2id has no such limit.

- **Lowering `access_ttl` no longer brings revoked tokens back.** A revoke denylisted for the configured `access_ttl + leeway`, so after the TTL was lowered — the usual incident response — a family revoked afterwards had its entry expire before its older, longer tokens did, and they verified again (RFC 7009 §2.1). Every mint now records its lifetime in the denylist store under a key of its own, living exactly as long as that lifetime, and revocation covers at least the longest one still alive. One key per lifetime rather than a shared maximum read and then written, so a concurrent shorter mint cannot overwrite a longer one; and read for the guard and store the revoking action was built for, not the ambient guard. The verifier and challenge decoder also cap `leeway` at five minutes (RFC 7519 §4.1.4: "some small leeway").

- **A two-factor challenge is spent atomically.** It was checked at the start of a redemption and marked spent at the end, so two concurrent redemptions with different valid factors (two recovery codes, or a code and a recovery code) both minted a session. The spend is now an atomic claim, the primitive the passkey challenge and TOTP replay marker already use, and the loser is refused.


- **Access tokens carry `auth_time`, and the multi-factor step-up allowance ages out.** `auth_time` (OpenID Connect Core §2) is when the session was signed in: stamped at sign-in, reserved like `amr`, and stored with the family in the same `amr` column (as `{"amr":[…],"auth_time":…}`), so every rotation carries the real sign-in time and no migration beyond `amr`'s is needed. A family stored before the time was — a bare `amr` list — carries no `auth_time`, and its multi-factor allowance fails closed until the next multi-factor sign-in. A password-only step-up on an account with a second factor is accepted inside an `mfa` session only for `confirm.mfa_max_age` (default 86400, `LUKK_CONFIRM_MFA_MAX_AGE`) after that sign-in — NIST SP 800-63B-4 §2.2.3 lets an AAL2 session reauthenticate with one factor while it is an AAL2 session, whose overall limit SHOULD be about a day. `mfa` used to vouch for the whole 30-day refresh life.

- **Every lockout read and write happens inside the sign-in timebox**, with the account lookup. A real account has two lockout counters and an unknown identifier one, so with `features.lockout` on a wrong password cost 15 queries against 7, outside the box where the gap could be averaged into an existence oracle.

- **The leeway cap reaches every decoder.** It was applied only to access tokens, so with a large `LUKK_LEEWAY` a two-factor challenge, step-up confirmation or passkey challenge stayed valid for up to a day past its expiry. `Lukk::leeway()` is the one clamp.

- **Upgrading a weak hash at sign-in no longer reverts a concurrent password change.** The sign-in reads the row once, at the start. Rehashing by saving that model wrote `Hash::make(<old password>)` over a reset committed in between, and the session, fingerprinted from the rehashed model, survived the password-unchanged check. The upgrade is now a conditional write that replaces only the hash this sign-in checked; losing that race to a concurrent upgrade of the same password adopts the winner's hash instead of revoking the session. Eloquent users only: another provider offers no conditional write, so lukk skips the upgrade there.

- **Two 500s on unauthenticated input paths now answer as rejections.** A passkey `ceremony_id` is validated as the UUID lukk issues, so an arbitrary string no longer reaches a cache key — a long one overflowed the database cache store's key column on PostgreSQL and strict MySQL. And a stored TOTP secret the library cannot read (non-base32, too short: a restored backup or a hand-edited row) now fails the code and is reported, where it threw on every sign-in.

- **`DELETE /auth/sessions/others` answered 204 having revoked nothing** when the bearer carried no `fid` (a co-issuer's token, in the verify-only topology). Revoking nothing is the right action — "others" is defined relative to this session, and with no family to except, revoking everything would take the caller's own session, which is the one thing this route promises not to do — but reporting it as success was not: the user pressed "log out my other devices", the client read success, and an attacker's session stayed live for the rest of its `refresh_ttl` with nothing saying so. It now answers **409** and names `DELETE /auth/sessions`. `Lukk::actingAs()`, which presents no bearer at all, keeps the no-op.

- **Both login rate-limit cache keys folded distinct identifiers together.** They reach `Illuminate\Cache\RateLimiter` directly, so the md5 `ThrottleRequests` applies never happens and only `cleanRateLimiterKey` does — `htmlentities()` plus an entity-shortening regex, a many-to-one map that sends `a&b@x.com` and `aab@x.com` to the same key. Both are valid addresses. Since `clear()` cleans the key the same way, signing in successfully as the look-alike reset the victim's **per-account** counter — the IP-independent backstop that exists so a distributed attacker cannot get `max_attempts` guesses per IP against one account. The identifier is now hashed into both keys, which also puts the `|` delimiter out of reach of a field carrying no charset rule.

  **A narrower fold remains, by design.** `LoginRateLimiter::normalize()` transliterates and lowercases before hashing, so `аdmin@x.com` (Cyrillic а) and `admin@x.com` share a bucket, and a victim's failures can briefly throttle a look-alike account. A success no longer clears the shared IP-independent bucket, so the look-alike's owner can no longer reset the victim's count — see the look-alike entry above. Keying the buckets on the resolved account instead would make the throttle's timing an account-existence oracle.

- **A degraded `rate_limits` block relaxed the controls it was meant to preserve.** The generic limiter loop fell back to 30 attempts per 60 s for every key — 6x looser than the shipped value on `confirm` (5), `email_verification` (6) and `password_reset` (6). Reachable rather than hypothetical: `rate_limits.confirm` only arrived in 0.5.0, and an application that ran `config:cache` before then is never backfilled, because `mergeConfigDeep` early-returns when the configuration is cached. Each key now falls back to the value `config/lukk.php` ships, and a test pins that no key can degrade to a looser limit than the shipped one.

- **A revoked family's denylist entry could expire before its access tokens.** Its TTL came from `lukk.access_ttl`, which is exact only while every token's `exp` really is `iat + access_ttl`. Lowering `access_ttl` in response to a suspected leak and then forcing a logout wrote an entry far shorter than the leaked token's remaining life, so it started working again mid-incident; a rebound `TokenIssuer`, which owns `exp` and is told nothing about `access_ttl`, under-covered every revocation permanently. The TTL is now the longer of the configured window and the remaining life of the token the caller presented.

- **`POST /auth/confirm-password` answered 500 on a non-string password** — the only endpoint in the package casting request input with no validation behind it, on a security-sensitive route. It now validates through a `ConfirmPasswordRequest` and answers 422. The existing test claimed to cover "a non-string one" but its cases were all values a `(string)` cast handles quietly; an array is the one that does not.

- **An undecryptable passkey 500'd the unauthenticated login route with the ceremony already burned.** A rotated `APP_KEY` without `app.previous_keys`, or a corrupt row, escaped as a server error from a path that had already spent the challenge — so every attempt cost one and a passkey-only account was locked out with no usable signal. An unreadable credential now reads as one that does not match. The TOTP path already guarded exactly this.

- **`ConfirmPasswordUnchanged` hashed the refresh token with `sha256` directly** instead of the `TokenIssuer::hash()` seam every other lookup uses, so under a rebound issuer the lookup missed and the family revoke behind the password-change race silently became a no-op.

- **A non-scalar `jti` or `fid` 500'd, and missed the denylist.** `exp` and `sub` were type-checked and these were not, so a co-issuer token carrying `"jti": ["a","b"]` raised "Array to string conversion" — and, worse than the 500, cast to the literal `Array`, so a revoked family stopped matching (RFC 8725 §3.10). `ChallengeToken::decode()` already hardened this; the access path had not. Challenge `sub` now also refuses the empty string, for parity.

- **A missing `lukk` config block took the whole application down.** `LukkServiceProvider::config()` was declared `array` with no default, so installing the package into an application that had already run `config:cache` returned null into a typed return — a TypeError thrown from `boot()`, not from the auth routes.

- **`Passkey` serialized its COSE key.** The model carried no `$hidden`, unlike its sibling `RefreshToken`, so an integrator serializing `$user->passkeys` published `public_key` and the `aaguid` that fingerprints the authenticator's make and model.

- **A sign-in checked against a password that was then changed or reset no longer keeps its session.** Change and reset write the new hash, then revoke the account's sessions. A sign-in that had already checked the OLD password, and wrote its session after that revoke read the table, survived it — the one sign-in a reset exists to shut out when an account is being recovered. On the two-factor path the window was the whole `challenge_ttl`, since the password is checked at login and the session started at redemption. A password sign-in now starts its session, then re-reads the password (`ConfirmPasswordUnchanged`, from the primary — see below): if it changed since the check, the session is revoked and the caller gets the ordinary wrong-password `422`. Each side commits before it reads, so one sees the other. A two-factor challenge now carries a fingerprint of the password it stands in for (`pwf`: an HMAC of the stored hash under `app.key`, never the hash) — a passkey sign-in that continues to a two-factor challenge carries one too, of the account's current password — and is refused at redemption if that password changed; a challenge without one — a co-issuer's, or one minted by an earlier release in the minutes around an upgrade — is refused too, and the user signs in again. The refusal comes BEFORE the second factor is checked, so it spends nothing: no recovery code is burned, no TOTP code is marked used, and no session is started. A passkey sign-in that completes without a challenge checks no password and is unaffected.

  **What it relies on.** The re-read must be authoritative: for an Eloquent provider lukk forces it onto the primary connection; a custom `UserProvider` must not answer `retrieveById` from a replica or a cache. Nothing may wrap the sign-in, change or reset requests in a database transaction — a transaction-per-request middleware on those routes reopens the race (on InnoDB it makes the re-read return the very snapshot the check took). With `Lukk::authenticateUsing` the baseline is the stored password read right after the callback, since the callback may return a model without the password loaded; a change before that read is not caught. Rotating `APP_KEY` keeps in-flight challenges valid only through `app.previous_keys`; deployments that share `LUKK_SECRET` to redeem each other's challenges must share `APP_KEY` too.

- **Logout-all could revoke a session that started while it ran — in the table only.** The bulk revoke behind logout-all, sign-out-others and password change/reset reads the user's live families, denylists them, then revoked by the user's query rather than by those family ids. Under PostgreSQL READ COMMITTED (a fresh snapshot per statement) and InnoDB (whose UPDATE reads the latest rows), a sign-in committed between the read and the update was revoked too: never denylisted, never returned to the caller, and signed out on its next refresh with nothing to show why. Both passes are now limited to the ids that were read, as `revokeFamily()` already was: a session started during the call survives it, on every path including password change and reset. For those two that is a deliberate choice, not an oversight — the only sign-in that can land in that gap is one racing the OLD password, and one that completes a moment later always survived anyway, so revoking inside the gap alone never closed that race; it only made the outcome depend on a few milliseconds of timing. A replacement `RefreshTokenRepository` should revoke by the ids it read, as the contract docblock now says.

- **An unset per-guard `features.two_factor` skipped the second factor.** A per-guard override resolving to `null` — `'features' => ['two_factor' => env('ADMIN_TWO_FACTOR')]` with the variable unset — survives the guard merge and beat the global `true`, and login read it as `?? false`: an account that had enrolled got a session on its password alone (ASVS 5.0 6.3.4, 16.5.3). Only a value somebody set — `false`, `0`, `'0'` — now switches enforcement off; `null`, a blank `.env` line (`''`) or a missing key still challenges an enrolled account, and `POST {path}/two-factor-challenge` mounts on that same rule, so no account is challenged without somewhere to answer. The management routes (enrol, confirm, disable, recovery codes) still need the flag switched on, so on an unset flag an account that loses its authenticator can spend its recovery codes but not regenerate them — set the flag explicitly either way. Accounts that never enrolled are unaffected.

- **Logout-all and logout-others could denylist nothing.** Both computed their denylist TTL as `access_ttl + leeway` with no defaults, and no `lukk` key is guaranteed at runtime: a config cached before a key existed gets no backfill, and the merge backfills on key *existence*, so a per-guard `'access_ttl' => env('LUKK_ADMIN_ACCESS_TTL')` with the variable unset survives it as null. The two reads then added to 0, and `Cache::put()` with a non-positive TTL forgets the key instead of writing it — so `DELETE /auth/sessions`, the "sign me out everywhere" button, answered `204` while every access token it had just revoked in the database kept working until it expired. The guarded read that `RevokeSession` already had is now shared by all three revoke actions.

- **Two-factor login bypassed `block_unverified_login`.** The password path checked the challenge before the verification gate, and the challenge-redemption route minted a session without asking, so enrolling a second factor exempted an unverified account from the policy that password-only and passkey logins enforced. Login now refuses before issuing a challenge — the same 403 at the same point as the password-only path, after the credential check, so it tells a caller nothing new and never lets a recovery code be spent on a login that will be refused — and redemption refuses a challenge that outlived the account's verified state. `emailUnverified()` is also read through `Lukk::guardConfig()`, so a per-guard override is honoured.

- **`LogoutResponse` read the global `cookie_mode`.** `EmitsTokens` sets the cookie per guard; logout now clears it per guard, so a guard that opted into cookie mode gets its `__Host-refresh-{guard}` cleared.

- **A passkey challenge could be redeemed twice under a race.** `Cache::pull()` is get-then-forget. Redemption now claims the challenge with an atomic `add()` — the primitive the TOTP replay defence already uses — keyed on the challenge value, so exactly one concurrent request wins.

- **`DELETE /auth/sessions/others` cleared the caller's refresh cookie in cookie mode.** It answered through `LogoutResponse`, which ends the *caller's* session client-side, while the route keeps that session alive server-side — the client could no longer refresh and was logged out at its next refresh. It now answers a bare `204` directly (same status and empty body as before, so clients such as lukk-js `revokeOtherSessions()` are unaffected) and sets no cookie. A rebound `LogoutResponse` no longer applies to this route: it is a fixed acknowledgement, not a swap seam.

- **A logout racing a refresh could leave a live token behind on PostgreSQL.** Rotation checks the denylist under its row lock, which catches a revoke that started first — but not one whose denylist write lands after that check and before the rotation commits. PostgreSQL's `UPDATE` then took its snapshot before the successor committed, blocked on the parent row, re-checked only that row and missed the successor, which rotated again once the denylist entry expired. `revokeFamily()` and the bulk revoke (logout-all, revoke-others, password change and reset) now run a second `UPDATE`, whose fresh READ COMMITTED snapshot sees the committed successor; the bulk pass is limited to the families already denylisted. MySQL was unaffected. Pinned in `tests/Concurrency/`.

- **`lukk.guards` set to `false` or `''` took down route registration.** Both mean "no extra guards", and `isMultiGuard()` read them that way, but `(array) false` is `[0 => false]`: the routes file mounted a guard named `0` and hit a `TypeError` while booting, and `Lukk::guardNames()` listed that phantom guard. Both now treat a non-array `guards` as empty.

- **A malformed `lukk.guards` is refused at boot, with a message naming the problem.** A numeric guard name — under `guards`, or as the default `lukk.guard` — becomes an integer array key that lukk cannot address by name. Before, it failed later with a `TypeError` while the routes registered, or a misleading "no `lukk.guards.{name}` config block". A list of names (`['admin']` instead of `['admin' => [...]]`) and a truthy scalar are refused too, each with its own message.

- **An empty or null `lukk.username` could sign in the wrong account.** `config($key, $default)` applies the default only to a MISSING key, so a null `lukk.username` — or an empty `LUKK_USERNAME=` line, which no `??` catches — made sign-in look users up by the column `''`. On SQLite that compiles to `"" = ?`, a comparison of two string literals that is true for every row: the first account matched any identifier, and its password signed in whoever typed it. MySQL and PostgreSQL refused the query instead, so sign-in failed outright. The identifier column is now read in one place, `Lukk::usernameField()`, which falls back to `email` for an unset, null or empty value; sign-in, registration, `lukk:release` and the account export and erasure all use it.

- **The default guard and route path are read the same way everywhere.** `lukk.guard` had the same null-becomes-`''` problem in the routes, the refresh-token trait and several other readers, so a null value made some of them treat `''` as the default guard and others `api`; one symptom was `lukk:prune` never pruning the default guard's orphaned passkeys under multi-guard. `Lukk::defaultGuard()` is now the single reader (unset, null or empty → `api`; a numeric name is still refused at boot), and a null `lukk.path` mounts the routes at `auth` rather than at the root.

- **`lukk:release` looked the account up in the wrong table when the default guard's provider differed.** Sign-in resolves the default guard's users from `lukk.user_provider`; the command read `auth.guards.{guard}.provider` for every guard, so where the two differ it reported "no lock found" for a lock that exists. Both now resolve through `Lukk::userProviderName()`, as does the passkey prune.

- **The account export omitted lockout counters** that erasure deletes (GDPR Art. 15 completeness). `GET /auth/account/export` gains a `lockouts` section — purpose, attempts, and timestamps, never lukk's internal subject keys — reached through the same three key spaces and guard scoping as the erasure sweep. `LockoutRepository` gains `summariesForSubjects()` (see the upgrade guide).

- **Password reset is padded to a wall-clock budget, like forgot-password.** Every failure answered the same `422`, but a known address with a pending token row paid a bcrypt check of the presented token that an unknown one did not, and the broker's own 200 ms box is shorter than one derivation at cost 12 — so the response time said which addresses had an account. The reset is now boxed in `password_reset.timebox_micros` (one second by default); a successful reset returns early.

- **Input that is not valid UTF-8 answers `422`, not a 500 on PostgreSQL.** A form body can carry any bytes, and PostgreSQL refuses an invalid sequence in a query parameter (SQLSTATE 22021). Valid UTF-8 is now required of the sign-in identifier, the passkey `credential.id` on `POST /auth/passkeys/login` and `/auth/confirm-passkey` (looked up before anything verifies it), and registration's `name` and a non-email `lukk.username`, which reached the INSERT and the uniqueness query. An email address was already refused by the `email` rule; a passkey's name gets the same check on enrolment. The sign-in password is deliberately left alone: it never reaches SQL, and registration, reset and change-password accept any bytes, so refusing them at sign-in would lock out an account whose password was set that way.

- **A committed rotation or sign-in no longer turns into a 500 when the longest-lifetime record fails.** `LongestAccessTtl::record()` ran after the commit unguarded, so a cache error or a lock timeout left the successor committed and the parent consumed while the client got an error — and its retry past the grace window read as a replay and revoked the family. The record is advisory: a failure is reported and the pair returned. A lock that cannot be had in time falls back to the unlocked write rather than throwing.

- **A negative `leeway` no longer shortens a revocation.** The verifier clamps `leeway` to 0..300 (`Lukk::leeway()`), but the denylist TTLs (family revoke, logout's `jti` entry) and the unclaimed-session window added the raw value, so `-120` let a revoked family's access token verify again for its last two minutes, and put the claim window inside the original token's acceptance band. Every reader now uses the clamped value.

- **Secrets are kept out of stack traces.** The presented refresh token, bearer tokens, challenge and confirmation tokens, passwords, TOTP and recovery codes and the TOTP secret are `#[\SensitiveParameter]` wherever lukk takes them as an argument — on the `TokenIssuer::hash()`, `TokenVerifier::verify()`, `TwoFactorProvider` and `TwoFactorAuthenticatable::useRecoveryCode()` contracts too — so a logged exception or an error tracker no longer carries them.

- **An asymmetric signing key is no longer read and decrypted under the rotation's row lock.** The issuer is bound per resolution, so every rotation started with an empty key memo and its first sign — inside the transaction — read the key file and, with a passphrase, decrypted it while holding `SELECT … FOR UPDATE`. `RotateRefreshToken` now loads the key before the transaction opens (after the reject short-circuit, so an unreadable key cannot pre-empt reuse detection). HS256 is unaffected.

- **Two malformed headers no longer get past type checks.** A challenge or confirmation token whose `typ` header is not a string raised a `TypeError` (a 500) instead of being refused; an access token whose `aud` is a JSON object was accepted when one of the object's values matched, through an `(array)` cast. Both are refused (RFC 7519 §4.1.3: `aud` is a StringOrURI or an array of them).

- **`lukk:prune` no longer fails every day on a service without the `refresh_tokens` table.** It is scheduled on every install, a verify-only resource server included, and the refresh-token sweep had no table check. It now checks for the table on the refresh-token model's own connection, as the passkey and lockout sweeps do.

- **`DELETE /auth/sessions/others` names the revoke-all route where the guard mounts it.** Its `409` said `DELETE /auth/sessions` whatever the guard's `path`, pointing a caller on a custom `lukk.path` or an extra guard at a 404; it now reads the answering route's prefix, and names no route where `features.logout_all` is off.

- **The recovery-code count reports the size of the set actually issued.** `GET two-factor/recovery-codes` reported `total` from raw config while generation clamps it to 1..100, so a configured 500 read as "100 of 500 left".

- **Confirming a pending two-factor secret the key cannot decrypt answers `422`, not a 500** (an `APP_KEY` rotated without `previous_keys`, a corrupt row), as the challenge path already did.

- **The user-carrying events serialize the user as an identifier.** `PasswordChanged`, `TwoFactorAuthenticationConfirmed`, `TwoFactorAuthenticationDisabled`, `RecoveryCodesGenerated`, `PasskeyRegistered` and `PasskeyDeleted` now use `SerializesModels`, as Laravel's `PasswordReset` does. A queued listener — the documented way to email the user — otherwise put the whole model into `jobs.payload`, and on failure into `failed_jobs`: the password hash, the encrypted TOTP secret and the recovery-code hashes.

## [0.6.0] - 2026-08-22

### Added

- **Account erasure and export (GDPR Art. 17 / Art. 15)** — a step-up-confirmed `DELETE /auth/account` that revokes every session, erases every artifact lukk owns, and deletes the user; plus `GET /auth/account/export` returning the personal data lukk holds. `features.account_deletion` defaults to **on**: erasure is a legal right, and a default of off means most installs quietly don't offer one.

  Order is the substance. The identifier is captured **first**, because one of the three lockout key spaces (`idn:<normalized identifier>`) is reachable only through it — the others are `id:<user id>` for login failures against a real account, and the bare user id for the step-up and two-factor caps. The raw identifier is never itself a key, so a sweep keyed on it matches nothing. Sessions are revoked **before** anything is deleted, denylist first, so every access token dies immediately and a failure later leaves the account unreachable rather than half-erased and still usable. Everything else runs in **one transaction**, including your `AccountDeleting` listener and the delete callback: a partial erasure is an account that cannot log in, cannot be recovered and cannot be erased again. This is deliberately the opposite trade to `RotateRefreshToken`, which keeps consumer code *out* of its transaction — erasure is rare, one-shot and irreversible, so atomicity beats lock duration. Note the revocation in step 2 is **not** rolled back by an aborting listener: the subject keeps their account and is logged out everywhere. `AccountDeleted` fires after the commit, carrying identifiers rather than the model.

  **An account is `(guard, id)`, not `id`.** Erasure and export are both guard-scoped. Providers are separate tables, so `users.id === admins.id` is the ordinary multi-guard case — an unscoped erasure destroyed an unrelated admin's refresh tokens (a permanent logout of a live account, with no `revoked_at` to explain it and no denylist entry, since revocation *was* scoped), and an unscoped export handed one subject another's session history, which Art. 15(4) forbids.

  Both routes are gated on a dedicated **`lukk.account.delete`** ability, deliberately not covered by `lukk.account`. Step-up alone does not close them to machine tokens: `RequireConfirmation` binds a confirmation to the *subject*, not to the token that earned it, so a pinned token can present one the human's session earned. And folding erasure into `lukk.account` — which already meant "manage my credentials" — would have handed every already-issued token carrying it the power to destroy the account, silently, on upgrade.

  `lukk:prune` now also removes **orphaned passkeys**, whose user no longer exists. Nothing else ever did: a passkey has no expiry, and erasure only reaches accounts deleted through lukk's own route, so a row deleted directly left the credential id, device name and last-used timestamp behind permanently. Each guard is swept against **its own** provider table, and a row lukk cannot attribute is left alone — retention is the safe direction for a daily, irreversible sweep.

  The erasure path also sweeps the **configured** password broker (`lukk.password_reset.broker`), not the default one. Laravel doesn't garbage-collect that table, so a pending reset row keeps a plaintext address of someone who asked to be forgotten for as long as the table lives; targeting the default broker missed it *and* deleted from whatever table the default pointed at, keyed on email alone, which under multi-guard is shared.

  The default disposal is **`forceDelete()`** where the model supports it. `delete()` on a `SoftDeletes` model is a silent no-op for Art. 17 — name, email, password hash and a live encrypted TOTP secret all survive — and leaves the subject neither erased nor able to return, since re-registering hits the database unique index that the `unique` validation rule's soft-delete scope ignores.

  **`Lukk::deleteUserUsing()`** replaces what happens to the user row — anonymize instead of delete, keep a tombstone, honour a retention obligation. Two things the callback then owns that deletion got for free: two-factor material lives in columns *on* the user row, so anonymizing without clearing them leaves a working authenticator attached to the erased account, and the identifier column is usually personal data in its own right.

  The export is the **auth slice only** — sessions, passkeys, whether two-factor is on — and says so loudly, because a half-answer that looks whole is worse than no endpoint. Credential material is deliberately excluded: a TOTP secret, recovery codes and refresh-token hashes are not personal data a subject benefits from receiving, they are secrets whose only use is authenticating *as* them, and Art. 15(4) says the right of access must not adversely affect others. What is included is the *fact* of each credential.

  Both routes sit behind **step-up confirmation**, never authentication alone — a stolen access token must not be enough to destroy an account or pull out everything lukk knows about someone. Step-up is not what keeps machine tokens out, though; that is `lukk.account.delete`. A pin carrying `lukk.account` can earn its *own* confirmation, and until confirmations became session-bound (below) a pin could also present one the human's browser earned.

  **`features.gate_auth_routes = false` does not reach the erasure gate.** That flag buys back pre-0.6 reach for tokens issued before abilities existed; these routes did not exist then, so honouring it would not restore an old behaviour but hand a narrow machine token an irreversible new one — a `['ci.deploy']` token could earn its own confirmation and destroy the account, arriving on upgrade with no re-consent.

- **Two-factor is guard-aware.** Three linked defects, all reachable only under [multiple guards](https://stsepelin.github.io/lukk-docs/multiple-guards) and all pinned by regression tests.

  `twoFactorRequired()` read `config('lukk.features.two_factor')` from the **global** block instead of `Lukk::guardConfig()` — the precise pattern already recorded as exploitable for `features.abilities` and `gate_auth_routes`. A guard that switched two-factor off was still challenged; one that switched it on was not.

  A secondary guard mounted `login` but **not** `two-factor-challenge`, so an enrolled account there was told to complete a challenge it had no endpoint to complete: enrolled, challenged, and bricked. The redemption route now mounts wherever `login` does, with its own per-guard throttle. Management routes (enrol, confirm, disable, recovery codes) stay on the default guard — they need step-up, and their absence locks nobody out.

  The challenge carried **no guard binding**, so isolation rested entirely on the consumer giving each guard a distinct issuer/audience/secret. Under the minimal shape — only `provider` and `path` differ — a challenge asserting "admins.1 cleared the first factor" was redeemable as "users.1 cleared the first factor". Not a second-factor bypass, since the attacker still needs that account's second factor, but a **first-factor** one: a session on a guard whose password was never presented. Challenges now carry a `gid` claim, matched strictly at redemption, with `null` still admitting a co-issuer that predates it.

- **An unreadable two-factor secret no longer bricks the account, and an empty one is refused.** `Crypt::decryptString()` throws on a stale `APP_KEY` rather than returning null, and the secret was read before either branch — so an APP_KEY rotation made every attempt a 500, and because `VerifyTwoFactorChallenge` catches only `ValidationException` the reserved lockout slot was never released. The account was locked permanently out of the recovery codes that exist for exactly that situation. The secret is now resolved lazily inside the TOTP branch, where a throw and a null mean the same thing, so a recovery-only attempt never touches it.

  `''` is refused alongside `null` in both `ChallengeTwoFactor` and `ConfirmTwoFactor`. An empty key is what a `(string) null` cast produces, and while the bundled provider rejects it, `TwoFactorProvider` is a documented swap seam — the guarantee cannot live in one implementation of it.

- **Challenge tokens require a well-formed `exp` and `jti`.** `firebase/php-jwt` does not require `exp`, so a co-issuer could mint a challenge that never expires, against "challenge single-use + short TTL". `consume()` also read `exp` *after* the second factor had verified, where an uncaught throw 500'd the request and left the challenge unburned.

- **A `guard` column on `passkeys` (breaking — see the [upgrade guide](UPGRADE.md))** — every passkey read and write is now guard-scoped, like `refresh_tokens` since 0.4.0. Without it the table was addressed by `user_id` alone, and under multi-guard the providers are separate tables where `users.id === admins.id` is the ordinary case.

  The lookup that matters is `findByCredentialId`: a WebAuthn assertion arrives with a credential id and **no user**, so that query is what decides who just authenticated — unscoped, an admin's credential resolved on the users guard. Erasing a customer also destroyed a live administrator's second factor, exporting a customer disclosed that administrator's device name and last-used timestamp (Art. 15(4)), and `lukk:prune` — scheduled **daily** — decided orphanhood against a single users table, which made every other provider's credential orphaned by construction.

  `NULL` means the single-guard default and behaves exactly as before, and `lukk:prune` checks for the column rather than assuming it — naming a column an upgraded install doesn't have would throw nightly on MySQL/PostgreSQL and, on SQLite, silently degrade to a string literal that matches nothing, leaving the new sweep inert while reporting success.

  **Backfill the column if you adopted `lukk.guards` after enabling passkeys**, or those rows become invisible to every guard: unusable, but deliberately never deleted. The reverse also needs a cleanup step and fails *open* — removing a guard leaves its stamped rows visible to the default guard, which here means its authenticator logs in as whoever holds the same id. Both directions are in the [upgrade guide](UPGRADE.md); the same asymmetry has always applied to `refresh_tokens.guard`.

  `PasskeyRepository` gains **`existsByCredentialId()`**, the one method that must stay *unscoped*: the unique index is global, so registration has to ask whether any guard holds an id before writing it. The registration challenge cache key is now guard-scoped too, so a colliding id can't let one account's in-flight ceremony clobber another's.

- **A step-up confirmation is bound to the session that earned it.** It carries the `fid` of the refresh-token family that re-verified the credential, and `RequireConfirmation` refuses one from a different family with `423` and `reason: confirmation_session_mismatch`.

  A step-up asserts "the person at this keyboard re-proved themselves just now". Bound to the subject alone it was bearer authority across **every** token that subject held — so a machine token, which can never earn a confirmation itself because the earning routes are ability-gated, could present the one the user's browser earned. Enabling two-factor, registering a passkey, regenerating recovery codes and erasing the account were all reachable that way. `fid` is stable across rotation, so refreshing mid-window keeps the confirmation valid, and BFF mode is unaffected.

  Matching is **strict**, so `null === null` still admits the co-issuer topology — a token minted by another service sharing the secret legitimately carries no `fid`, and neither does a confirmation earned by it — while an *unbound* confirmation is refused to a bearer that has one. The loose branch would only have bought a `confirm.ttl`-wide window in which the old bypass still worked.

- **Abilities / scopes** — coarse, stateless authorization carried in the access token. `Lukk::abilitiesUsing(fn ($userId, $context) => ['orders.read', 'orders.*'])` mints a `scope` claim; `lukk.ability:a,b` gates a route on **any** of them and `lukk.abilities:a,b` on **all** (Sanctum's split, so the semantics are the ones people already expect); `$user->tokenCan('orders.read')` via the `HasTokenAbilities` trait.

  The wire format is the registered `scope` claim, space-delimited (RFC 6749 §3.3, RFC 9068 §2.2.3), so an API gateway or a non-lukk verifier can read it without knowing about lukk. `*` grants everything and `orders.*` grants the namespace — but a wildcard only ever appears in the *grant*, never in the check, so a caller can't widen their own question by asking `tokenCan('orders.*')`. Grants are validated against the RFC's `scope-token` charset and a malformed one **throws**: the claim is space-delimited, so `['orders.read admin']` would otherwise parse back as two abilities and hand out an `admin` nobody issued — reachable the moment ability names come from data.

  **Deny by default, and inert until configured.** Without `abilitiesUsing` no claim is minted at all and tokens stay byte-identical to 0.5.0. Once it's set, a token with no `scope` grants nothing — because adding `lukk.ability:admin` to a route while forgetting to configure abilities should fail loudly, not wave everyone through. `scope` also becomes **reserved**: `tokenClaimsUsing` can no longer set it, in either direction — it can't forge a grant, and an empty grant can now *erase* one it set (`abilitiesUsing` returning `[]` for a suspended user must not still mint `admin.*`).

  The second argument is a `TokenContext` carrying the **guard** and the session's **family id**. A multi-guard install serves different audiences often enough that `['*']` for a customer token and `['*']` for an admin one are not the same grant; an object rather than more positional parameters means the next field added won't break closures already written.

  By default abilities are **re-derived on every mint**, not frozen at login, so revoking one takes effect within `access_ttl` instead of lasting the life of the refresh token. A session that must instead carry a **fixed** grant — a personal access token, an impersonation session capped below the target user — passes its abilities to `StartSession`, which stores them on the family row (new nullable `scope` column, see the [upgrade guide](UPGRADE.md)) and replays them through every rotation. `NULL` means derived; a value means pinned.

  `$user->tokenCan()` reads the token the guard verified onto the **request**, not state on the model. Sanctum's model-state equivalent has two failure modes this avoids: a model the guard never touched (`$order->user`, a fresh `find()`) silently denies what the token was actually granted, and a model that outlives its request answers from the *previous* token's grant.

  A gate reached with no credential at all answers **401**, not 403 — a 403 tells a client "you are known and refused", so it stops retrying and never learns it just needs to log in. Insufficient scope answers 403 with `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"` (RFC 6750 §3.1), naming what would have sufficed. The gates are registered **after** `Authenticate` in the kernel's middleware priority, so `['lukk.ability:x', 'auth:api']` and the reverse order behave identically.

  `Http\Resources\UserResource` publishes the token's `abilities`, which is the only channel a BFF-mode client has — it never sees the access token that carries the claim. **Absent, not empty**, when abilities aren't in play: `[]` means "in use, granted nothing" (hide the UI) while an absent key means "this server doesn't use abilities" (show it), so an install that upgrades without opting in doesn't find its UI blanked. Only emitted for the token's own subject, so a user list doesn't stamp every row with the reader's grant.

  `Lukk::actingAs($user, $guard, $abilities)` stands in for a token in tests, and **throws outside the test environment**. The container binding it uses is not the safety net it looks like: `forgetScopedInstances()` drops the resolved instance but leaves the binding — a closure holding the token by value — registered, so on a long-lived worker the next request re-resolves the same token. Rather than ship a mechanism whose only safe use is the one nobody enforces, it refuses to run in production; grant abilities there by minting a token that carries them.

  A grant pinned to **nothing** stays nothing. `toScope()` collapses an empty grant to `null` and `null` on the column means "derive", so a zero-scope token — a capped impersonation session, a PAT granted nothing — would have widened to the subject's *full* grant on its first refresh. The column stores `''` for a pinned-empty grant and keeps the two states apart.

  **Name abilities after resources, not after facts about a person.** An ability name travels in the `scope` claim past every proxy and gateway, is published on the user resource, and appears as a literal string in your JavaScript bundle. `hiv_clinic.records.read` is a special-category disclosure at each hop; `clinic_a.records.read` is not. lukk validates the *syntax* of a name (RFC 6749) and can say nothing about its meaning.

  A new `features.abilities` flag (default off) exists for one case: grants that come **only** from an explicit `StartSession` pin, with no `abilitiesUsing` callback. Configuring the callback turns the feature on by itself, so most installs never touch it. Without the flag lukk can't distinguish a token pinned to *nothing* from a server that doesn't use abilities — and the client would then render the full privileged UI for the most restricted token you can issue.

  **`Events\TokenAbilityDenied`** fires when a verified token is refused a route for its scope. lukk announces every other security transition it owns, and a token probing for what it can still reach looks exactly like a run of these — without it a deployment has no lukk-side signal at all. Deliberately an event and not a log line: ability names travel widely enough already. The payload carries the *route's* requirement, never the caller's granted list, since a queued listener would serialize it.

  **`abilitiesUsing` is resolved before the refresh transaction opens**, not inside it. The callback is application code documented as hitting a permission store, and running it under `FOR UPDATE` made lukk's correctness depend on someone else's query: a slow lookup extended the lock on every refresh, taking locks in the opposite order deadlocked against it, and on PostgreSQL a callback that swallowed its own SQL error left the transaction aborted — where `COMMIT` becomes a silent `ROLLBACK`, so lukk handed back a valid access token whose successor row was never written and the client discovered it was logged out one refresh later. Nothing but lukk's own statements and pure crypto run inside the lock now, pinned by two PostgreSQL tests in `tests/Concurrency/`.

  **`Lukk::assertGuardsIsolated()` now refuses to boot a `lukk-jwt` guard that has no `lukk.guards` block of its own.** Pre-existing since multi-guard shipped in 0.4.0: the check keyed on `config('lukk.guards')`, so a second guard declared only in `config/auth.php` skipped it entirely — and `guardConfig()` then deep-merged nothing over the top-level block, handing that guard the default guard's secret *and audience*. Audience is the control that stops one guard's token verifying on another, so a customer's access token authenticated as whatever the second guard's provider returned for the same id: a different user, in a different table, HTTP 200, no boot error and nothing in the log.

  **lukk's own `DELETE /auth/sessions` and `/auth/sessions/others` are gated on `lukk.sessions`.** A token pinned to `['ci.deploy']` — the most restricted thing the API can issue, refused by every gated route in the application — could still revoke every *other* session and log the account out everywhere, because lukk's own routes were gated on authentication alone. Only a **pinned** grant is gated, marked by a new `pin` claim stamped just on those tokens: a derived grant is a live human login and keeps managing its own sessions, so nothing changes for an existing install and nobody has to discover a new ability name. `logout` and `refresh` are deliberately not gated — they act on the calling session alone, and a personal access token has to be able to end and renew itself. Turn the whole thing off with `features.gate_auth_routes`.

  **`tokenClaimsUsing` is resolved before the refresh transaction too.** Moving the mint inside the transaction (above) left the claims hook under the row lock, since the issuer was the one resolving it — the same consumer callback, the same permission-store read, the same three hazards. Both hooks now run ahead of the transaction, behind the same reject short-circuit, so neither is asked about a token lukk is going to refuse and neither can throw early enough to pre-empt reuse detection. The issuer no longer resolves either: it stamps what the Action hands it. Per-login claims still beat the hook's, and standard claims still beat both.

  **`features.abilities` and `features.gate_auth_routes` are read through the active guard's config**, not the global block. `guardConfig()` deep-merges `lukk.guards.{name}` over the top level, so a deployment can switch a feature on for one guard — and both flags ignored that while failing *open*: the claims hook could become the authorization layer on the second guard, and a guard could not switch the session gate on for itself.

  **The pinned-token boundary covers account-security operations too**, via a second ability `lukk.account`: both step-up routes (`confirm-password` *and* `confirm-passkey` — gating one and not the other would make it decorative) and `POST /auth/password`. Step-up is the gateway to everything that takes an account over permanently — enrolling a passkey, disabling two-factor, regenerating recovery codes — and changing the password both rotates the credential and sweeps every other session. All of it needs the password, so a pinned token could never do it silently; but "a machine token must not log the account out everywhere" and "a machine token may enrol a permanent authenticator" cannot both be the rule.

  **Pinned-ness is confirmed against the database when the `pin` claim is absent.** The claim is stamped by `TokenIssuer`, a documented swap seam, so an implementation that forwards `$abilities` but forgets `TokenContext::$pinned` produced a genuinely pinned token that lukk's own gates waved through — and note the asymmetry that made this worth a round trip: the `scope` half of the same seam fails *closed* and loudly, this half failed *open* and silently. Costs one indexed lookup, only when the claim is absent, on routes that already revoke sessions or verify a password.

  Refresh-token rows are written with `forceFill`, not mass assignment. `Lukk::useRefreshTokenModel()` is a documented seam, and a subclass declaring `$fillable` silently dropped `scope` — turning a token pinned to one ability into the subject's *full* derived grant on its first refresh, session management included, because `familyIsPinned()` reads the same column that was never written and so collapsed with it. `StartSession` additionally refuses to hand back a pinned session whose pin didn't reach storage.

  Scope is deliberately coarse: it says what a *token* may do, never which *records* it may touch. Per-object authorization stays your Policies and Gates (OWASP API1 — BOLA).

## [0.5.0] - 2026-08-21

### Added

- **Change password while signed in (`POST /auth/password`)** — the counterpart to the forgot-password flow, without the email round-trip. Re-verifies the current password, applies `Password::defaults()` to the new one, revokes every **other** session, and fires `Events\PasswordChanged`.

  Asking for the current password is the whole security story: a stolen access token alone must not be enough to take an account over permanently, which is exactly what changing the password would do. Because it checks the same secret as login and step-up, it runs on the **same** budget — the `lukk-confirm` throttle and, with `features.lockout` on, the `confirm` counter. Two independent allowances for guessing one password is just a larger allowance. A success clears **both** the `confirm` and `login` counters, since the failures they hold were against a password that no longer exists — otherwise a user who was being brute-forced, noticed, and changed their password stayed locked out of login on every other device.

  Other sessions die; the one it was done from survives. (A token carrying no `fid` — one minted by a co-issuer sharing the secret — identifies no session here to preserve, so every session is revoked rather than none.) Changing a password is what someone does when they think another party is in the account, so leaving those sessions alive would defeat the point — but logging the user out of the tab they just did it in is a bad answer to a good instinct. The session to keep is read from the caller's own verified token, so it can't be pointed at someone else's to spare it from the sweep.

  On by default (`features.change_password`), like `logout_all`: it needs no configuration, and refusing a signed-in user the ability to change their own password is not a sensible default. Turn it off where passwords live in an identity provider.

- **Account lockout (`features.lockout`, opt-in, off by default)** — an absolute cap on *consecutive* failed authentication attempts, satisfying **NIST SP 800-63B §5.2.2** ("the verifier SHALL limit consecutive failed authentication attempts on a single account to no more than 100"). The existing throttles are decaying windows: they bound a *rate*, not a *run*, so lifetime guesses were unbounded — roughly 7,200/day against a 6-digit TOTP code. Covers both password login (keyed on the normalized identifier) and the two-factor challenge (keyed on the user), each with its own counter and guard-scoped, so burning one doesn't spend the other's budget.

  Counters live in a new `lukk_lockouts` table (publish `lukk-lockout-migrations`) because "consecutive" can't be expressed by a cache entry that expires — and a cache flush would silently release every lock. `Lockout` storage sits behind a `LockoutRepository` contract, so it's swappable like `RefreshTokenRepository`.

  **A hard lockout is also a denial-of-service primitive** — anyone who knows an address can burn its budget deliberately — which is why it ships off, and why release has five paths: any successful authentication clears the run (that's what "consecutive" means), a **password reset** clears it (proving control of the address is stronger evidence than the password, so this is the self-service way out), `php artisan lukk:release <subject>` for operators, the repository API for your own code, and an optional `lockout.release_after` that auto-lifts and bounds the denial. Every path fires `AccountReleased`, so an audit log sees the unlock and not just the lock. A locked account answers **423** rather than 429, because with manual-only release "retry later" would be untrue. `AccountLocked` fires once on the transition — a locked-out user gets no other signal.

Two honest caveats. Setting `release_after` **trades the strict reading**: a run broken by time rather than by a success is no longer "consecutive", so 100/3600s is a 100-per-hour cap — which is exactly OWASP ASVS V2.2.1, and better than the package's current ~1,200/hour, but not §5.2.2's lifetime bound. And a recovery code is deliberately **not** gated by a two-factor lock: at ~119 bits it isn't brute-forceable, and gating it would strand a user whose second factor an attacker burned on purpose.

- **`Lukk::rateLimitKeyUsing()`** — replace the identity every lukk throttle buckets on. The default is the request IP; override it when the source address isn't the right bucket for your deployment (a shared API gateway, a tenant, a CDN's own visitor token).

### Changed

- **Every throttle now collapses an IPv6 caller to their `/64`.** A subscriber is typically handed a whole `/64`, so keying on the full address let one visitor mint effectively unlimited buckets and walk through every per-IP limit. IPv4 is unchanged, and an IPv4-mapped address (`::ffff:1.2.3.4`) is unwrapped to its IPv4 form rather than collapsing every mapped address into one shared `::/64` bucket — the same unwrapping applies to NAT64's `64:ff9b::/96`, so an IPv6-only client population behind a translation gateway isn't bucketed as one caller. This only starts to matter once the address is genuinely the visitor's — behind a BFF it is the proxy until the deployment forwards the real client — which is exactly when per-IP limits stop being a single shared bucket and start needing to hold.
- **The authenticated email-verification resend gained a second, per-user limit** alongside the per-IP one. Rotating IPs is cheap once per-IP buckets are genuinely per-visitor, so a single session could otherwise resend without limit. It reuses the endpoint's existing `max_attempts`/`decay_seconds` (no new configuration; Laravel applies every returned limit and the tighter wins) and is guard-scoped, resolving the user from lukk's own guard — the same limiter also guards the unauthenticated signed verify route, where the app's default guard could otherwise share a bucket with a colliding id from an unrelated provider. Registration deliberately did **not** get the same treatment: a duplicate signup is a `422` from the `unique` rule and sends no mail, so an identity bucket there would bound nothing while handing anyone a remote, IP-independent way to deny a chosen address the ability to register.
- **`rate_limits.ipv6_prefix`** (env `LUKK_RATE_LIMIT_IPV6_PREFIX`, default `64`) tunes the IPv6 mask. `64` suits residential and mobile networks; lower it if your attackers hold larger delegations, or raise it toward `128` if your users share a `/64` — an office or campus LAN does.

### Security

- **A full audit pass closed 24 findings.** Three parallel white-box reviews against the release candidate (auth/rate-limiting/lockout, token crypto/rotation/revocation, optional features/data-at-rest), each asked to prove findings by reproducing them. Every finding is fixed and pinned by a regression test; the two accepted trade-offs are documented under [Known limitations](https://stsepelin.github.io/lukk-docs/security#known-limitations). Highlights beyond the step-up work below:

  - **Concurrency could overrun the lockout cap** (`RACE-1`). The gate was a plain read outside the transaction that later counted, so N concurrent requests all passed it and all reached the credential check — realized verifications were `max_attempts + concurrency`. Attempts are now reserved: incremented transactionally, then compared against the cap.
  - **A family revoke could lose a race with a concurrent rotation** (`RT-1`), leaving a live token behind so that a logout-all or a reuse kill undid itself once the denylist entry expired. Rotation re-checks the denylist after persisting the successor. Reasoned from PostgreSQL's READ COMMITTED semantics; **not reproduced** — the caveat is recorded rather than dropped.
  - **The refresh token was accepted from the query string** (`RT-2`), putting a 30-day opaque credential into access logs and `Referer` headers (RFC 9700 §4.3.2).
  - **The bulk revokes denylisted after the DB write** (`RT-3`), inverting the ordering `RevokeSession` documents — a cache failure partway left families revoked but still authenticating.
  - **`/auth/forgot-password` was timing-distinguishable** (`PWD-1`): the broker's `Timebox` pads a fast path but cannot claw back bcrypt's overrun, so one request classified an address.
  - **Passkey login skipped `block_unverified_login`** and never resolved the user (`PK-2`).
  - **Every guard shared one refresh cookie** (`COOKIE-1`) and **container-resolved actions targeted the default guard** (`GUARD-2`).
  - Plus bounds on the reset endpoints, a clamp on `recovery_codes`, a guard against an `array` denylist store in production, and a loud failure for a `lukk.guards` entry named after the default guard.

- **`Events\RefreshFamilyForked`** — the grace window mints a sibling rather than revoking, which is what stops a multi-tab or SSR client logging itself out; the cost is that a thief racing inside the window gets a parallel chain that never trips reuse detection. That was previously invisible. Advisory by design — acting on it automatically would mean revoking on suspicion.

- **The account lockout keys on the resolved user, not on the submitted identifier.** `transliterate(lower(trim(...)))` is many-to-one across distinct accounts — `аdmin@example.com` with a Cyrillic а, or plain `ADMIN@example.com` on any engine whose unique index compares binary — so two real accounts shared one counter. Because a password reset releases on that subject, anyone who controlled a look-alike account could lock the victim, reset their own password to clear the shared lock, and repeat indefinitely; the §5.2.2 cap collapsed back to the decaying throttle it exists to replace, and two legitimate look-alike accounts locked each other out as collateral. Subjects are now `id:<primary key>` when the identifier names an account and `idn:<normalized>` when it doesn't — the fallback matters, because an identifier that names no account must still accumulate a counter or `423`-vs-`422` would answer "does this account exist?" for free. `lukk:release` resolves a pasted address the same way, as written and then normalized, so the operator flow is unchanged.

- **Step-up confirmation is now guard-scoped.** `lukk.confirm` resolved its verifier from the `lukk.set-guard` middleware, which only runs inside lukk's own route groups — never on a consumer's own `['auth:admin', 'lukk.confirm']` route. The guard silently fell back to the default, so an admin route verified step-up against the **users** guard's key and audience. With user ids colliding across two providers (the norm for auto-increment), a confirmation earned on the users guard satisfied the admin gate — defeating the control that exists to limit what a stolen access token can do. The mirror was broken too: an admin's own confirmation, minted at `admin/auth/confirm-password`, could never satisfy the gate. It now verifies against the guard that actually authenticated the request.

- **A junk `recovery_code` no longer bypasses the two-factor lockout.** The recovery-code exemption was keyed on the field being *present*, but the challenge action checks the TOTP code first — so attaching any junk recovery code skipped the §5.2.2 cap and carried on brute-forcing the 6-digit space, including against an already-locked account. The exemption now requires a recovery-code-**only** attempt; a recovery code on its own still releases the lock, which was the point of the exemption.

- **A passkey `signCount` of 0 no longer defeats clone detection.** The regression check also required the *incoming* counter to be non-zero, so a clone presenting `0` against a credential that had reached `10` was accepted — a textbook WebAuthn L3 §6.1.1 regression — and the `0` was then written back, resetting the ratchet so the genuine authenticator could never trip it either. The test is now on the stored counter alone, and the counter never moves backwards. Synced passkeys are unaffected: their stored count is `0` forever, which is what keeps them from ever being flagged.

- **Bounded the lockout subject in bytes.** `LoginRequest` caps the identifier at 255 *characters*, but transliteration expands up to ~6x — 43 copies of `㈱` pass validation and arrive as 258 bytes, overflowing `lukk_lockouts.subject` and, on Laravel's default `database` cache store, the `cache.key` column: MySQL `1406` / PostgreSQL `22001`, surfacing as a 500 on the unauthenticated `/auth/login`. Long subjects are hashed rather than truncated, so two distinct identifiers can't be folded into one shared bucket by the fix itself.

- **Step-up confirmation is throttled and lockable.** `POST /auth/confirm-password` and `/auth/confirm-passkey` had **no rate limit at all** — only the guard. Since password confirmation re-verifies the *same* secret the login route throttles two ways, anyone already holding an access token (a stolen one, an XSS'd one, a shared device) had an unmetered password oracle sitting behind the sudo gate. Both routes now run a `lukk-confirm` limiter (`rate_limits.confirm`, default 5/60s, plus `lukk-{guard}-confirm` for the additional guards), keyed on **both** the user and the IP — the per-user bucket is the load-bearing one, because a caller with a stolen token is a single identity behind however many addresses they care to use.

  With `features.lockout` on, a run of failed password confirmations also counts toward the **NIST SP 800-63B §5.2.2** cap under a new `confirm` purpose, keyed on the user id (the caller is already authenticated, so unlike the login lock there is a resolved account and no enumeration concern). Two escapes beyond `release_after` and `php artisan lukk:release <id> --purpose=confirm`: a **successful login** clears it — proof of the same password, and something an attacker holding only a token cannot produce — and so does a **password reset**, after which the counted failures are against a password that no longer exists. `confirm-passkey` is metered but deliberately **not** locked: an assertion is a signature, not a guessable secret, so the throttle there is DoS protection rather than brute-force defence.

### Fixed

- **`php artisan lukk:release` could not release a `two_factor` or `confirm` lock.** Those subjects are user ids, recorded verbatim, but the command lower-cased every subject — which breaks a ULID (uppercase Crockford base32) on every engine that compares binary (PostgreSQL, SQLite). The documented operator escape hatch silently released nothing. Normalization now applies only to `login`, whose subject really is a normalized identifier.
- **The lockout's insert-race recovery was itself a 500 on PostgreSQL.** A failed `INSERT` aborts the entire transaction there (`25P02` on every subsequent statement), so the `catch` that exists to absorb two concurrent first-failures could not run. The insert is now nested, so Laravel emits a `SAVEPOINT` and the rollback stays local.
- **`POST /auth/register` bounds the identifier length** (`max:255`, matching `name` and `password`). `email` + `unique` against an unbounded string was avoidable work for an anonymous caller (ASVS V2.1).

## [0.4.0] - 2026-07-07

### Added

- **Multiple guards** (multi-audience isolation). Declare a second isolated audience — an admin API alongside the users API — under `config('lukk.guards')` plus a `lukk-jwt` guard in `config/auth.php` (whose `provider` lukk reuses). Each guard carries its own cryptographic token identity: its own **`audience`** (required, distinct) and optionally its own `secret`/keys/`issuer`/ttls. A token minted for one guard is rejected by another on the audience check (and signature, when keys differ) — **before any user is resolved**, so it can never resolve `User::find($sub)` on the wrong guard (RFC 8725 §3.9 / OWASP ASVS 5.0 §9.2.3–9.2.4). Refresh-token families and logout-all are scoped by a nullable `guard` column, so revoking one guard's sessions can't touch another's even when user ids collide (`users.id == admins.id`). Routes auto-mount per guard under a per-guard `path` and optional **`domain`** (subdomain isolation). lukk **refuses to boot** unless every guard declares a distinct, non-empty audience and mounts at a distinct path/domain, and every extra guard is declared in `config/auth.php`. `php artisan lukk:secret --guard=admin` writes `LUKK_ADMIN_SECRET`; `HasRefreshTokens::lukkGuard()` binds a model (e.g. `Admin`) to its guard. An app with no `lukk.guards` behaves exactly as before.
- **Registration** (opt-in via `features.registration`). A first-party `POST /auth/register` that mirrors login: it creates the user, fires `Illuminate\Auth\Events\Registered` (so the email-verification listener sends the link), and returns the same token pair a login yields (BFF or cookie mode) — or a 2FA challenge if the new user is already enrolled, or a `201` no-session shape when the account can't log in yet. The built-in default create works with the **stock Laravel `users` shape out of the box** (`name` + the identifier + a hashed `password`). Fully customizable: `Lukk::registerUsing()` owns user creation (closure or invokable class-string), `Lukk::registerValidation()` (or rebinding `RegisterRequest`) owns the fields/rules, and `RegisterResponse` is rebindable like the other response contracts. `registration.login` (default true) toggles auto-login vs. create-only (`201`, sign in separately). Per-IP throttled (`lukk-register`); a duplicate identifier is a `422` (the only enumeration a registration form inherently has). Backward compatible — off by default.
- **Configurable login identifier** (`lukk.username`, default `email`). Fortify-style: set it to `username` (or any unique column) and both login and registration authenticate by that column instead of email — the login request field, the constant-time credential lookup, the per-account throttle bucket, and the registration validation/create all follow it. Defaults to `email`, so existing behavior is unchanged.

### Changed

- **`refresh_tokens` schema: added a nullable `guard` column** (for multi-guard family isolation; it stays null and unused under a single guard). ⚠️ **Pre-1.0 schema change** — because lukk is `0.x` with no stable installs, this was folded into the existing `create_refresh_tokens_table` migration rather than shipped as a separate one. **Fresh installs are unaffected** (publishing `lukk-migrations` creates the column). A pre-release install that already ran the old migration must add the column manually — `ALTER TABLE refresh_tokens ADD COLUMN guard VARCHAR(255) NULL` — or drop and re-run the migration. See the [UPGRADE guide](UPGRADE.md#upgrading-to-040-from-03x). Future schema changes (post-1.0) will ship as additive migrations.

## [0.3.0] - 2026-07-02

### Added

- **Password reset** (opt-in via `features.password_reset`), built on Laravel's password broker. `POST /auth/forgot-password` emails a reset link pointing at your SPA (`password_reset.frontend_url?token=…&email=…`) and always returns a generic `200` (no user enumeration, throttled `lukk-password-reset`); `POST /auth/reset-password` consumes the token, sets the new password, fires `Illuminate\Auth\Events\PasswordReset`, and — unless `password_reset.revoke_sessions` is false — **revokes every existing session** (refresh families + denylist) so a session that predates the reset can't survive it. Relies on the framework-default `password_reset_tokens` table + an `auth.passwords` broker (`password_reset.broker` selects a non-default one; no lukk migration). Both endpoints are enumeration-safe — reset returns one generic `422` for every failure. See the [password-reset docs](https://stsepelin.github.io/lukk-docs/password-reset).

## [0.2.0] - 2026-07-02

### Added

- Optional `Lukk\Http\Resources\UserResource` — an extendable base API Resource for your `user.endpoint` that emits the fields the lukk-js client reads (the identifier + a derived `email_verified` boolean), so `useLukkAuth().user` / `verified` work out of the box. Extend it and override `fields()` to add your own; a bare model or your own resource still works too (lukk doesn't own your user endpoint — this is a convenience).
- `cookie.secure` config (env `LUKK_COOKIE_SECURE`, default `true`) gating the direct-mode refresh cookie's `Secure` attribute. Set it `false` **only** for local development over plain http — a browser drops a `Secure` cookie on http even on localhost, so the session wouldn't persist; lukk then also strips the `__Host-` prefix from the cookie name (that prefix requires `Secure`). Never ship `secure=false`.

### Security

- **IP-independent per-account login lockout** (`LUKK_LOGIN_ACCOUNT_MAX_ATTEMPTS`, default 20/min). The login limiter now throttles per account too, not just per email+IP, bounding a distributed brute force that rotates source IPs against a single account. The unknown-user path stays constant-time.
- **Atomic TOTP single-use.** The one-time-use guard for a TOTP code now uses an atomic cache `add` (was a `has` + `put`), closing a same-instant double-accept race under concurrency.

### Fixed

- Passkey registration now requests a **resident (discoverable) credential** (`residentKey: required`, user verification advisory), so passwordless / usernameless login works — the ceremony previously didn't request one and discoverable login failed with `NotAllowedError`.

## [0.1.4] - 2026-07-01

### Added

- **Email verification** (opt-in via `features.email_verification`). First-party, stateless verification that rides Laravel's framework-default `email_verified_at` + `MustVerifyEmail` (no lukk migration). A **signed link** (`GET /auth/email/verify/{id}/{hash}`, outside the JSON-forcing group) verifies and content-negotiates a redirect to your SPA (`email_verification.frontend_url`, with `?verified=1`) or a `204` for a JSON client; `POST /auth/email/verification-notification` resends (throttled `lukk-email-verification`). A `lukk.verified` middleware gates routes with a **409** when the email isn't verified (read fresh off the user, never a token claim), and `email_verification.block_unverified_login` optionally refuses login with a **403**. lukk points Laravel's `VerifyEmail` notification at its signed route; verification fires the standard `Illuminate\Auth\Events\Verified`. See [docs/email-verification.md](docs/email-verification.md).

## [0.1.3] - 2026-07-01

### Added

- `lukk.force-json` middleware alias. Attach it to your *own* `auth:api` routes (`Route::middleware(['lukk.force-json', 'auth:api'])`) to get a clean `401` JSON instead of the guest-redirect `500` on an `Accept`-less request — surgically, without globally disabling the guest redirect (which would also drop a real web login's redirect). It reuses the existing `ForceJsonRequest` middleware (ordered ahead of `Authenticate`), is opt-in (registers nothing global until you attach it), and works in verify-only services (`routes => false`) too.

### Changed

- Auth request validation moved to FormRequests (`LoginRequest`, `TwoFactorChallengeRequest`, `PasskeyAssertionRequest`, `PasskeyRegistrationRequest`). A malformed input (e.g. `code[]=x`) now renders a `422` instead of a `500`.
- `lukk:prune` now keeps revoked-but-unexpired refresh tokens (deletes only rows past `expires_at`), so a replay of a revoked token still resolves to reuse detection (`reuse` + family cascade + `RefreshTokenReused`) instead of a generic reject; the rows self-delete once they expire.

### Security

- **Passkey `user_verification` now defaults to `required`** (was `preferred`). Passwordless login and passkey step-up are single-factor (possession), so enforcing user verification (biometric/PIN) makes them phishing-resistant (AAL2). Set `LUKK_PASSKEY_UV=preferred` if you must support authenticators that can't verify the user.
- `RevokeSession` writes the denylist entry **before** the DB revoke, so a mid-operation cache failure can't leave a family's access tokens live after its refresh tokens are revoked.
- Challenge/confirmation tokens (2FA, passkey step-up) sign and verify through the same `KeyRing` as access tokens — staying alg-pinned and working under an RS256/ES256 deployment (previously hard-coded to the symmetric secret, which broke asymmetric setups).
- The 2FA trait hides `two_factor_secret` / `two_factor_recovery_codes` from model serialization (matching Fortify), so returning your `User` model in a response no longer exposes the encrypted secret / hashed recovery blobs.
- The passkey ceremony now **pins the accepted COSE signature algorithms explicitly** (ES256 + RS256, matching the advertised `pubKeyCredParams`) instead of inheriting `web-auth/webauthn-lib`'s transitive default — so a future library-default change can't silently widen the allowed set (defense-in-depth; WebAuthn L3 §5.3/§7.2).

### Performance

- `KeyRing` now memoizes its verification `Key` set and loaded public-key PEMs per instance, so an asymmetric (RS256/ES256) deployment no longer re-reads key files or re-allocates a `Firebase\JWT\Key` on every token verification.

### Fixed

- JWKS EC coordinates are now left-padded to the curve field size (RFC 7518 §6.2.1.2). `openssl_pkey_get_details` strips leading zero bytes, so roughly 1 in 256 coordinates was published a byte short and strict JWKS consumers would reject the key. Only affects RS256/ES256 (specifically ES\*) deployments serving `GET /auth/jwks`; the default HS256 setup publishes an empty set and is unaffected.

## [0.1.0] - 2026-06-28

### Added

Core token model:

- Short-lived HS256 access JWTs with full claim set (`iss/aud/sub/fid/jti/iat/nbf/exp`, `typ=at+jwt`).
- Optional asymmetric signing (RS256 / ES256) behind the same `TokenIssuer`/`TokenVerifier` contracts, for split auth-service / verify-only-API deployments: a `kid`-addressed key set, signing-key rotation with an overlap window (a retired key keeps verifying its live tokens), a `GET /auth/jwks` endpoint (JWK Set built without any extra dependency), and a `lukk:keygen` command. The algorithm is pinned from config and never read from the token header — the RS256↔HS256 confusion defense.
- Opaque, rotating refresh tokens (sha256 at rest) with reuse detection and family-cascade revoke.
- Concurrency grace window so single-flight refreshes don't trip reuse detection.
- Cache-backed denylist (by `jti`/`fid`) for instant revocation.

Guard & endpoints:

- `JwtGuard` request guard (`lukk-jwt` driver) and resource controllers: `POST /auth/login` + `/refresh`, `POST /auth/logout`, and `DELETE /auth/sessions` (revoke all) / `DELETE /auth/sessions/others` (revoke all but the caller, via `RevokeOtherSessions`).

Extensibility:

- Swappable contracts (`TokenIssuer`, `TokenVerifier`, `RefreshTokenRepository`, `Denylist`, response contracts).
- Static `Lukk` hub (`authenticateUsing`, `useRefreshTokenModel`, `actingAs`) and `HasRefreshTokens` trait.
- `Lukk::tokenClaimsUsing()` to add custom claims (e.g. roles) to the access token; standard claims cannot be overridden.
- Multiple audiences: `LUKK_AUDIENCE` is comma-separated, so one token can be minted for several services; each verifies when its own audience is listed (a single audience stays a string). Enables a split auth-service / verify-only-API topology — see `docs/deployment.md`.

Security:

- `RefreshTokenReused` security event on reuse/revoked family kill.
- `Cache-Control: no-store` on token responses and constant-time login (no user enumeration).
- The access-token verifier enforces the `typ=at+jwt` header, so a 2FA / step-up *challenge* token (same key, iss and aud) can never be presented as a bearer access token.
- A coarse per-IP login cap (`rate_limits.login.ip_max_attempts`) on top of the per-account failure limiter, bounding password spraying across many emails.
- Passkeys require `rp_id` and `origins` to be configured (fail loud rather than silently weak origin validation); passkey verification failures return a 4xx, never an uncaught 500.
- In cookie mode the `__Host-` refresh cookie is `SameSite=Strict` (and cleared with matching attributes on logout).
- An unknown / expired / revoked / reused refresh token returns a clean `401` (self-rendering `InvalidRefreshToken`), never an uncaught 500, without leaking which reason.
- Config is **deep-merged** from the package defaults, so a published config that predates a nested key is backfilled — preventing a missing rate-limit key from resolving to `0` (which would lock out every login).
- Unified, configurable rate limits under `lukk.rate_limits` — `login`, `two_factor`, `refresh`, and `passkeys`, each `{ max_attempts, decay_seconds }`. Login keeps a dedicated failures-only limiter (keyed on normalized email + IP, clears on success); the rest are named limiters (`lukk-refresh` / `lukk-passkeys` / `lukk-2fa`) you can also override via `RateLimiter::for()`. Two-factor additionally throttles per account (`sub`).

Multi-factor (opt-in):

- Two-factor authentication (TOTP + recovery codes), opt-in via `features.two_factor` + `pragmarx/google2fa`: enrol/confirm/disable/regenerate endpoints, a recovery-code **count** endpoint (`GET /auth/two-factor/recovery-codes` — codes stay hashed, so only the remaining count is surfaced, never the values), and a `2fa+challenge` login step. Secret stored encrypted, recovery codes salted+hashed (single-use), intra-window TOTP replay protection, account-keyed challenge throttle, and `amr` claims (`["pwd"]` / `["pwd","otp"]`) on issued tokens. `Auth\ChallengeToken` is a generic single-use challenge primitive (reused by passkeys).
- Step-up ("sudo") confirmation: `POST /auth/confirm-password` (or `/auth/confirm-passkey`) mints a short-lived `confirmation_token`, and the `lukk.confirm` middleware gates sensitive routes behind it (423 Locked otherwise). Reusable for your own routes; the 2FA + passkey management endpoints use it.
- Passkeys (WebAuthn / FIDO2), opt-in via `features.passkeys` + a `WebAuthnCeremony` adapter: passwordless registration/login (→ tokens with `amr: ["webauthn"]`), credential list/delete, and passkey-based step-up confirmation. Stateless cache-backed single-use challenges (keyed by user for registration, opaque `ceremony_id` for login), sign-count regression detection (`Events\PasskeyCloneDetected`, never flags `0`), globally-unique credential ids, COSE public key encrypted at rest. Storage behind `Contracts\PasskeyRepository` (`passkeys` table). `rp_id` and `origins` are required (no weak fallback); `passkeys.user_verification` (default `preferred`, set `required` for biometric/PIN) gates login and step-up.

Commands:

- `lukk:secret` Artisan command to generate the 256-bit HMAC signing secret and write `LUKK_SECRET` to `.env` (modeled on `jwt:secret`/`key:generate`; supports `--show` and `--force`).
- `lukk:keygen` Artisan command to generate an RS256/ES256 signing keypair (prints the PEMs and the env to set).
- `lukk:prune` command for expired/revoked tokens, scheduled daily by default (opt out via `Lukk::disableScheduling()`).
